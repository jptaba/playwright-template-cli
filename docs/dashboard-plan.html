Dashboard in Seven Phases

One window on the suite: pull a story, see the cases it produced, run them, watch it happen, triage what broke, publish the result. Most of this is already written and tested — what is missing is a face on it.

The thesis

The pipeline this framework describes — story to cases to specs to a run to triage to a published result — is already built, stage by stage, as pure modules with CLIs in front of them. What it has never had is a single place to stand and watch it work.

So the dashboard is not new machinery. It is a fifth front end onto modules that already exist, the same way npm run onboard became a second front end onto planScaffold. That is why this can be built in slices that each ship.

One genuinely new engine: a reporter that emits events as a run happens rather than a model at the end. Everything else is presentation over existing data.

Three rules the build follows

These are not new — they are the pattern onboard and offboard already prove, written down so every phase is built the same way.

  • Logic in src/support/, I/O in tools/. Routing, validation and every refusal live in a module with no sockets and no filesystem, so they are unit-tested without either. The tool is the socket and nothing else.
  • The dashboard owns no data. It reads run-result.json, cases/, stories/, the history file. If it needs something those cannot answer, the answer belongs in a module, not in a page.
  • Anything that writes asks first. Loopback binding, a per-run token, and — for anything destructive or outward-facing — a typed confirmation. Already true of offboarding; it stays true of publishing.

The phases

0

The shell

no new features · makes every later phase possible

Turn the single onboarding page into a multi-page application: one server, shared chrome, a navigation rail, one place that defines the tokens. Onboarding moves in as the first page and keeps working exactly as it does now.

Builds
support/ui/shell.ts (page frame, nav, tokens), support/ui/router.ts (generalised from the onboarding router), tools/dashboard.ts
Reuses
Everything in onboarding/dashboard.ts — token check, loopback check, JSON helpers
Validated by
  • The existing onboard → offboard round trip passes unchanged, through the new shell
  • Every page's inline script parses (new Function, as now)
  • Router unit tests: unknown route 404s, non-loopback 403s, stale token 403s

Done when npm run dashboard serves onboarding at /onboard with no behaviour change, and npm run onboard still works as an alias.

1

Runs

read-only · the first thing worth opening the dashboard for

The last run and the ones before it. Totals by kind, the capability notes that say “not applicable for this target” rather than showing a silent zero, every failure with its error, its steps, and links to its trace and video. Plus the trend across runs.

Builds
A runs page and a run-detail page; an attachment route that serves files from test-results/
Reuses
RunResult, readHistory, buildTrend, laneOf
Validated by
  • Against a real run-result.json: totals rendered equal totals in the file
  • A run with a disabled capability shows “not applicable”, not zero
  • A flaky test reads as flaky, not as passed — the distinction the run model already makes
  • The attachment route refuses any path outside the results directory

Done when a run you did on the command line is fully readable in the browser without re-running it.

2

Running, live

the one new engine · the phase with real risk in it

Choose a target, projects and tags; press run; watch it happen. A second Playwright reporter writes one JSON object per event to a stream, the server relays it over server-sent events, and the page shows a lane per worker with the test each is on.

Builds
reporters/live-events-reporter.ts, an event schema, an SSE route, a two-slot run registry, the screencast fixture, cancellation
Reuses
The existing reporter stays as-is and still writes the canonical model at the end
Validated by
  • Run the framework project through it: every test appears, and the event totals equal the final run-result.json
  • Two runs at once each produce their own complete result — measured, and it currently fails: see below
  • Killing the browser mid-run leaves no orphaned process
  • The event stream is append-only and survives a page reload — reconnect replays

Watching it happen: three options, measured

A correction to an earlier claim of mine. I said video could not be streamed. That is true of Playwright's video recorder, which finalises its file only when the context closes — and false as a general statement. Both other options were tested against a real browser.

OptionWhat you seeCostVerdict

Headed is the answer to “watch it run”, and it needs no engineering at all. This dashboard is local-only, so the browsers are already on the machine looking at the screen — relaying pixels into a web page to display them on the same monitor is a long way round. The dashboard offers a Run headed toggle and Playwright does the rest.

Headed is not headless. A backgrounded window throttles timers, and some behaviour is focus-dependent — so a test can pass headed and fail headless, which is the mode CI uses. Headed is for watching, never for deciding whether something passes.

The embedded live view

Two runs at a time, and both are on screen. One cap, not two — a run you cannot see is a run you have to go and look for, and the whole point of the page is that everything happening is happening in front of you. It also removes a category of design: no rule for which run earns the picture, no queue, no run that behaves differently from its neighbour.

Each view is a tile in the run page at its embedded size, and expands to fill the window and back again. Expanding is a UI state, not a different stream — though it does re-request the screencast at a larger maxWidth, since sending 1280px frames into a 400px tile is waste and sending 400px frames into a full window is a blur.

Frame budget
~8 fps, 640px wide, quality 50 embedded — about 25 KB a frame, so two streams cost roughly 400 KB/s. The measured 45 fps at 72 KB is what it does unthrottled, and two of those would be 6 MB/s into a page.
Attaching
An opt-in fixture, switched on by an environment variable the dashboard sets for that run only. It must cost exactly nothing when unset — no CDP session, no listener.
Following the run
A worker runs tests one after another and each may open its own page, so the stream re-attaches per page rather than binding once to the first one.
A third run
Refused while two are going, with the reason and the two runs named. Not queued: a queued run starts unattended some minutes later, against an application whose state has moved, and nobody is watching when it does.

Two honest limits on the picture. The frame feed is Chromium-only, because it is a CDP capability — a Firefox or WebKit run shows that rather than a black rectangle. And it is pixels, one way: the tile is something you watch, never something you click into. Anything that looked interactive and was not would be worse than no picture at all.

Every managed case, its quality-gate score, and whether a spec implements it — matched on the practitest annotation every spec already carries. The two interesting lists are cases with no spec, and specs citing a case that does not exist.

Builds
A coverage view; a matcher between case ids and spec annotations
Reuses
loadCases, hashCase, cases/gate.ts, the catalog extractor
Validated by

  • A case with no spec appears as uncovered; the counts add up to the case total
  • Gate scores match what npm run cases:gate prints

Done when “what is not covered?” is one page rather than a manual cross-reference.

4

Stories into cases

the authoring loop · deliberately stops short of committing

Paste a Jira key, see the story and the acceptance criteria it yielded, draft cases from it, and review them as a diff. Anything that cannot cite a criterion verbatim is quarantined and shown as such.

Builds
A story view and a case-diff view
Reuses
pull-story, cases/author.ts, extractCriteria, wikiToPlainText, the case gate
Validated by
  • Against the existing fake-jira-server — no network, no credentials
  • A story with no identifiable criteria is rejected, with that as the stated reason
  • A drafted case that cites nothing is quarantined rather than shown as ready
  • Nothing is written outside cases/, and nothing is committed

It writes files and stops. The conventions put a person between authoring and publication on purpose — git is the staging area. A button that went from story to merged spec would be the exact loop those conventions exist to prevent, so this produces a diff to review and nothing else.

5

Triage

has ground truth to validate against, which is unusual and worth using

Cluster the failures from the last run, show what the rules settled and what they declined to settle, and let a person confirm or overrule each verdict. Quarantine candidates are ranked by rate, not count.

Builds
A triage view; a verdict-override store
Reuses
triage/cluster.ts, triage/rules.ts, triage/agent.ts, quarantine.ts
Validated by
  • The triage-fixture project — specs meant to fail with causes known in advance. Run it, triage it, compare against the expected category recorded beside each spec
  • A rule that classifies something the fixture calls different is a failure; a rule that declines a genuine judgement call is correct
  • Overriding a verdict does not silently edit the run model

Done when the agreement measurement the plan asks for is a number on a page rather than an exercise.

6

Publishing

outward-facing · the only phase that touches someone else's system

Post run results against their PractiTest cases, and open Jira defects for confirmed failures — one ticket per cluster, deduplicated on the fingerprint the client already computes.

Builds
A publish view with a preview of exactly what will be sent
Reuses
publish-practitest, publish-jira, defectFingerprint, cases/publish.ts
Validated by
  • Against the existing fake-practitest-server and fake-jira-server
  • Publishing twice opens one ticket, not two — the fingerprint holds
  • A credential never appears in a preview, a log or a response
  • Nothing is sent without an explicit confirmation, as with offboarding

This one leaves the building. A mistake here is visible to other teams and cannot be undone with git checkout. It gets the same treatment as removing a target: a preview of the exact payload, and a typed confirmation before anything is sent.

Order, and why

Phases 0–2 are the spine: a shell, the ability to read a run, and the ability to start one. After phase 2 the dashboard is already worth opening every day. Phases 3–4 are the authoring loop and 5–6 close it. Each ships on its own, and stopping after any of them leaves something coherent rather than half a feature.

What this will not do

  • Run more than two at once. Two, both watched. A third is refused rather than queued — a run that starts unattended later, against state that has moved, is the kind of result nobody trusts.
  • Let you click into the picture. A screencast is pixels one way. Something that looked interactive and was not would be worse than no picture.
  • Author a spec and merge it. Authoring produces a diff. A person and git stay in the loop.
  • Become a service. It binds to loopback, holds a per-run token, and is started by a person. Putting it on a network is a different product with a different threat model.
  • Replace the CLIs. Every phase is a second front end onto a module that keeps its command. CI does not get a browser.
  • Own state. No database. The committed files — cases/, the history JSON-lines, the quarantine list — stay the record.

Three questions, now settled

Two concurrent runs — and one thing that breaks

Two slots, both visible, no queue. Concurrency collides today though, and it is worth knowing exactly where before phase 2 starts. Two runs launched at once, each with its own --output: 

A: 315 ok    B: 315 ok    run-result.json: one file, 316 tests

Both runs finished. Only one canonical model survived.

--output already gives each run its own artefact directory, so traces and screenshots are fine. What is not fine is RUN_RESULT_PATH, a fixed constant in support/paths.ts — every run writes the same file and the last one wins. Same for the JUnit path in playwright.config.ts. Both need to read an environment variable, which is a small change and a prerequisite for this phase.

Two runs against one application share one login. With accountPool: 'static' and serverState: true — the scaffolder's own default — every worker in both runs is the same user, mutating the same cart, favourites and orders. That is not theoretical: it produced 409s, wrong cart contents and eventually a locked account on a real target. Concurrency is safe across different targets and for read-only projects; the dashboard warns when both runs point at the same one rather than refusing.

Where artefacts live — recommendation, with the numbers behind it

Measured, not estimated. One short two-page journey, traced and recorded: 2.9 MB of trace and 244 KB of video. A trace costs about twelve times what a video does, and carries far more — the DOM, the network, the sources.

Also worth knowing: locally this repository currently records almost nothing. trace is on-first-retry with retries: 0, and video is off. So the dashboard is not choosing where to keep artefacts that exist — it is choosing to start producing them.

ApproachAgainst it
Leave it in test-results/Cleared each run — only the last is inspectable, and concurrent runs overwrite each other
Copy artefacts out after each runDoubles the disk write, and races a run that is still writing
Zip per runA trace is already a zip; re-zipping saves nothing and makes it unopenable in the viewer
Per-run --output directoryNothing — Playwright writes there natively, first time, no copy

The recommendation:

  • .runs/<runId>/, gitignored, holding the artefacts, the canonical model and the event stream for that run. Passed as --output so Playwright writes there directly.
  • trace: 'retain-on-failure' and video: 'retain-on-failure' for dashboard-started runs. You want the trace when something broke, and a passing run that keeps 2.9 MB per test is how a laptop fills up.
  • Pruned on start, not on a timer, against two caps together: keep at most 20 runs and at most 2 GB, oldest first.

Self-critique. Three things I got wrong or nearly did:

  • A count cap alone is not enough. Twenty runs at retain-on-failure is a few hundred megabytes — fine. Twenty runs where somebody passed --trace=on is closer to 2.6 GB. The size cap is the one that actually protects the disk, and the count cap is what keeps the list readable. Both, or neither works.
  • My first instinct was to copy artefacts into a history directory. That is strictly worse than telling Playwright where to write in the first place — and it races a run that has not finished writing.
  • Keeping .runs/ inside the repository rather than in the OS temp directory is a deliberate trade: it clutters the working tree, and it is gitignored so nothing leaks, but temp directories get cleaned by the system and comparing last week's failure to today's is the entire point of keeping them.

Local only — settled, and here is what the question meant

The server binds to 127.0.0.1, so nothing outside the machine can reach it. The token stops a web page open in another tab from quietly POSTing to it — a page on any origin can reach localhost, and these endpoints write to the repository. That is the whole of it, and for a local-only tool it is the right amount.

Since CI stays headless and never opens this, there is nothing further to design: no accounts, no sessions, no network exposure. If that ever changes it is a different product, and the change should be deliberate rather than something that drifted.

Phase 0 is the only one that must be built before anything else can be. Everything after it is reorderable if a different slice turns out to matter more.
