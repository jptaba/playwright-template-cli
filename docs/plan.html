An AI-legible Playwright framework

A test automation stack with two authoring tracks — a Jira story becomes reviewed test cases, or an existing PractiTest case is picked up as written — and both end as running Playwright specs with a human in the review seat, not the typing seat. It covers UI journeys, API tests, contract conformance and the mixed tests that span them. The application under test is configuration, not code, with www.saucedemo.com as the reference target, and every environment it touches is a real running system.

Historical record. This is the plan as authored, before implementation, and it is kept unedited so the design decisions can be checked against what was actually built. It names www.saucedemo.com throughout as its reference target; saucedemo is now one of five onboarded applications on main, alongside toolshop, parabank, restful-booker and orangehrm. Framework code still names none of them. For the built system, read the handbook; for what the reference target taught the framework, docs/learnings.md.

Section 01The recommendation in one page

Eight decisions carry this design. Everything else follows from them.

Not just the browser — and not everything either

Decision

Four kinds of test in one framework: UI journeys, API tests, response-schema conformance, and the mixed tests that seed over the API, act in the UI and verify wherever the fact actually lands. Database reads are permitted, read-only, and last on the list of ways to assert anything. Two things are refused outright — unit tests, which belong in the application repositories, and consumer-driven contract testing, which belongs in the services' own pipelines and would be a fiction written from here.

Two authoring tracks, one generation spine

Decision

Track A starts at a Jira story: an LLM reads it and drafts test cases. Track B starts at a case already written in PractiTest. Both converge on one intermediate case format and one generation path, so there is a single place where a case becomes a spec, and both push their results back to PractiTest. Three AI roles, deliberately separated: the case author sees requirement text only, the spec generator sees the running application, the triage agent sees failures. Never one agent doing two of these.

The application under test is configuration

Decision

www.saucedemo.com is the reference target, selected by a TARGET profile and overridable per environment. Nothing anywhere in the framework hard-codes a URL. A profile carries base URL, credential references and a capability matrix, so a target without MFA skips the MFA suite by declaration rather than failing it — and phases 0 through 2 can be proven end-to-end before a single internal system is reachable.

Not classic POM — a four-layer split

Decision

Locators, actions, fixtures, specs. Page Object Model's open-ended class surface is exactly what makes LLM output drift. A closed vocabulary of typed fixtures and named business actions turns generation into a constrained choice rather than free composition.

Playwright's own agents are the generation engine

Decision

Playwright 1.56+ ships planner, generator and healer agents, installed with npx playwright init-agents --loop=claude|vscode. Do not hand-roll this. Drive them through @playwright/cli rather than the MCP server — roughly 4x fewer tokens for the same work — and wrap them with project skills that pull the test case in and push the result out.

Vault is never an MCP server

Decision

An authoring agent with tool access to Vault can read a live credential and bake it into generated source or a chat transcript. Secrets resolve at runtime, inside the test process, through a fixture. The agent only ever writes the reference, never the value.

Two OTP channels, one interface

Decision

Vault's TOTP secrets engine handles authenticator-app MFA; the mock SMTP inbox handles emailed codes. Both sit behind OtpProvider so a spec says await otp.get() and does not care which.

Reporting is best-effort, never build-blocking

Decision

PractiTest allows 20 instances per run POST and 30 API calls per minute. A custom reporter batches and throttles inside that envelope, and a reporting failure degrades to a warning plus an artifact — it never turns a green suite red.

Section 02What "AI-legible" actually means

The common reading is "write good docs so Copilot understands the repo." That is the weakest version of the idea and it does not survive contact with a 400-test suite.

A model generating a test is doing constrained search. Legibility is whatever shrinks the search space and whatever tells the model, without a human, that it went wrong. Three properties do the work:

1. A small, closed vocabulary

If there are eight fixtures and forty named actions with typed signatures, generation is close to multiple choice. If the model can call any method on any page object, plus raw page.*, it will invent loginPage.loginWithValidCredentials() — plausible, non-existent, and only caught at runtime.

2. Conventions that execute

A markdown rule saying "prefer getByRole" is advisory. An ESLint rule that fails on page.locator('.css-selector') is a feedback signal the agent can act on by itself. Every convention worth having should be expressible as a lint rule, a type, or a failing test. Documentation is the fallback for the rest.

3. Locators grounded in a real snapshot

This is what the Playwright MCP buys. Asked to write a login test from prose alone, a model guesses selectors from its priors. Given a live accessibility snapshot of the actual page, it reads them. Locator hallucination is the single largest source of dead-on-arrival generated tests, and exploration is the only real fix.

Classic POM helps with none of the three. It is a code-reuse pattern from an era when a human wrote every line, and it is being carried forward on momentum.

Section 03Framework shape

Four layers, each with one job and a hard rule about what it may not do.

L1 locators/Flat maps of named locators. getByRole first, then getByLabel, then getByTestId. No logic, no waits, no assertions.
L2 actions/Business verbs — submitExpenseClaim(data), completeMfaChallenge(). Composes L1. Returns data, not page objects. Asserts nothing except its own invariants.
L3 fixtures/The injectable surface: authedPage, secrets, otp, inbox, apiClient, testData. Handles setup, teardown, and worker isolation.
L4 tests/Thin specs, one per managed test case, carrying its PractiTest and Jira identifiers as annotations. All assertions live here.

The rules that make it hold

  • Specs never import from locators/ — if a spec needs an element, the missing thing is an action.
  • Actions never assert outcomes. Assertions in specs keep test intent readable and reviewable, which matters when a human is reviewing generated code at volume.
  • No waitForTimeout, ever. No CSS or XPath without an inline justification comment that lint recognises.
  • A spec body should be readable aloud to a manual tester and match their test case step for step.

The same four layers carry API and database work without modification — actions/ gains siblings rather than the model gaining a fifth layer. Section 05 sets that out.

What a generated spec looks like

test('TC-4821 · Expense claim rejected above approval limit', {
  annotation: [
    { type: 'practitest', description: '4821' },
    { type: 'jira',       description: 'FIN-2210' },
  ],
}, async ({ authedPage, expenses, testData }) => {
  const claim = testData.expenseClaim({ amount: 15_000 });

  await expenses.submitClaim(authedPage, claim);

  await expect(authedPage.getByRole('alert')).toHaveText(
    /exceeds your approval limit/i,
  );
  await expect(await expenses.statusOf(claim.reference)).toBe('Rejected');
});

Section 04The application under test

The reference target is www.saucedemo.com, and it is a setting rather than an assumption. Worth being precise about what "configurable" can and cannot mean, because the word usually hides a claim the code does not support.

What a target profile owns

One module per target, selected by TARGET, resolved once in playwright.config.ts and injected everywhere else through fixtures. No spec, action or locator ever names a host.

// targets/saucedemo/profile.ts
export const saucedemo: TargetProfile = {
  name: 'saucedemo',
  baseURL: process.env.BASE_URL ?? 'https://www.saucedemo.com',
  credentials: { source: 'vault', path: 'qa/saucedemo/pools/shopper' },
  capabilities: {
    mfa: 'none',            // 'none' | 'totp' | 'email'
    accountPool: 'static',  // fixed users, no leasing, no rotation
    serverState: false,     // cart lives in localStorage
    api:       { enabled: false },   // see section 05
    db:        { enabled: false },
    contracts: { enabled: false, spec: null },
  },
  suites: ['smoke', 'checkout', 'inventory'],
};

Two rules keep this honest. baseURL is read from the profile and nothing else — an ESLint rule (no-hardcoded-urls) fails any literal http(s):// outside config/targets/. And capabilities are consulted, not assumed: fixtures resolve against them, so otp on a mfa: 'none' target returns a provider that skips the test with a stated reason instead of hanging until timeout.

What a profile cannot abstract

This is where "configurable" is usually oversold. A base URL swap is a line of config; a different application is a different set of locators, actions and specs, and no amount of indirection changes that. So the split is explicit: fixtures/, integrations/ and support/ are target-agnostic framework; locators/, actions/ and tests/ are namespaced per target under targets/<name>/. Swapping targets selects a pack — it does not reuse one.

The payoff is that the framework itself gets exercised by a second, independent application from day one. A design that only ever runs against the app it was written for tends to grow assumptions about that app that nobody notices until the second target arrives.

The same spec shape, against the reference target

test('SD-012 · Checkout totals include tax', {
  annotation: [{ type: 'practitest', description: '5104' }],
}, async ({ authedPage, checkout, testData }) => {
  const items = testData.catalogItems({ count: 2 });

  await checkout.addToCart(authedPage, items);
  const totals = await checkout.completeThroughOverview(authedPage);

  expect(totals.subtotal).toBe(sumOf(items));
  expect(totals.tax).toBeCloseTo(totals.subtotal * 0.08, 2);
});

Why this particular demo app earns its place

  • It is reachable and stable. Phases 0 to 2 stop depending on Vault, Jira, PractiTest, the mail mock, or a firewall exception that has not landed. That removes the single biggest scheduling risk in section 22.
  • It has deliberately broken users. problem_user, performance_glitch_user and error_user produce genuine failures with known causes — which is precisely the fixture the triage agent in section 20 needs for measuring agreement rate, and precisely what a healthy application cannot provide on demand.
  • It has a locked-out user. locked_out_user gives a real negative-path login case without touching account lockout policy on a corporate directory.
  • It is small enough to be fully automated. A reference target that can reach 100% case coverage makes the coverage view in section 18 testable against a known answer.

Its credentials are public and trivial, and they still go through the secrets fixture, resolved from the same Vault path shape as every other target. Not because secret_sauce needs protecting, but because the moment one target is allowed to bypass the fixture, the lint rule stops being enforceable and the pattern erodes.

What this framework runs, and what it only talks to

Worth stating plainly, because test frameworks routinely acquire the habit of provisioning their own world and it never stops growing. This one provisions nothing. Every system it touches — the application under test, Vault, the mail tool, Jira, PractiTest, and any API or database behind them — is already running and operated by someone else. The framework holds a base URL, a credential reference and a client.

That has three consequences worth accepting deliberately:

  • No fakes, mocks or stand-in services in CI. A pipeline that spins up its own Vault or its own mail sink is testing a pipeline, not an environment. If a dependency is down, the run fails and says which one — that is a true result, and it is what the triage categories in section 20 exist to distinguish.
  • Environment readiness is a precondition, not a test step. A short reachability check at the start of a run turns "forty tests failed at login" into "the environment was not up", at a cost of a few seconds.
  • The only container anywhere in this plan is the GitLab job image, and that is a runner concern — one image: line pinned to Playwright's official build, not infrastructure this team operates. Nothing else needs Docker, locally or in CI.

Two caveats to settle in phase 0

  • saucedemo is a public internet host, and section 17 applies to it exactly as it applies to the npm registry: CI may simply not be permitted to reach it. That is an egress request, and it is a small one — a single hostname, HTTPS, no inbound path. Worth raising in the first week alongside the others, because a reference target the pipeline cannot reach is not a reference target.
  • It is not a proving ground. Green on saucedemo demonstrates that the wiring works. It says nothing about whether this design survives MFA, account pools, rotation or UI drift — see section 22, where this is the risk most likely to produce false confidence.

Section 05Beyond the browser — API, data and contract checks

The valuable tests in an enterprise suite are rarely pure UI. A claim is submitted in the browser, an API records it, a batch job posts it, and the check that matters spans all three. Playwright handles that better than its reputation suggests — with one thing on this list it should refuse to do.

Four kinds of test, one framework

The layers extend sideways, not downward

Nothing about the four-layer split in section 03 changes. It grows siblings: actions/ is the UI vocabulary, api/ is the HTTP vocabulary, db/ is the read vocabulary. All three are L2 — named business operations over a lower-level primitive — and all three obey the same rule, which is that they compose and return data but never assert.

L1 locators/ · endpoints/ · queries/The primitives. A named locator, a typed endpoint descriptor, a named SQL statement. No logic anywhere.
L2 actions/ · api/ · db/Business verbs per medium — checkout.submit(page, cart), ordersApi.create(data), ordersDb.findByRef(ref). Return data, assert nothing.
L3 fixtures/Gains api, db and contracts alongside authedPage, secrets and otp. Capability-gated — see section 04.
L4 tests/Unchanged. Every assertion still lives here, whichever medium produced the value.

The closed-vocabulary argument from section 02 applies with more force here, not less. A model asked to write an API test with a raw request.post available will invent endpoints, payload shapes and status codes with total confidence and no page to contradict it. A typed client generated from the same catalog the UI actions live in turns that back into multiple choice.

What a mixed test looks like

test('TC-4907 · Approved claim posts to the ledger', {
  annotation: [{ type: 'practitest', description: '4907' }],
}, async ({ authedPage, api, db, expenses, testData }) => {
  // Arrange over the API — seconds, not a five-step UI wizard
  const claim = await api.expenses.create(testData.expenseClaim({ amount: 250 }));

  // Act in the UI — this part is the actual subject of the test
  await expenses.approve(authedPage, claim.reference);

  // Assert where each fact really lives
  await expect(authedPage.getByRole('status')).toHaveText(/approved/i);
  expect(await api.expenses.get(claim.id)).toMatchObject({ state: 'approved' });

  await expect
    .poll(() => db.ledger.entryFor(claim.reference), { timeout: 30_000 })
    .toMatchObject({ amount: 250, type: 'DEBIT' });
});

Three properties make this the shape to aim for. Setup is API-driven, so the test is fast and its failures are about approval rather than about data entry. The UI step is the one thing under test. And the ledger assertion polls rather than sleeps, because the posting is asynchronous — expect.poll is the only acceptable answer to eventual consistency, and it is why the no-hard-waits rule survives contact with integration testing.

Projects, so the fast things stay fast

projects: [
  { name: 'setup:auth', testMatch: /auth\.setup\.ts/ },
  { name: 'api',        testDir: 'tests/api',      use: { browserName: undefined } },
  { name: 'contract',   testDir: 'tests/contract',  use: { browserName: undefined } },
  { name: 'e2e',        testDir: 'tests/e2e',
    dependencies: ['setup:auth'], use: { storageState: '.auth/${role}.json' } },
]

Separating them by project rather than by tag is what lets the merge-request pipeline run api and contract in full — they are quick enough — while the browser suite stays on its smoke subset. It also stops a browser being launched for a test that never needed one, which is most of the wall-clock time in a naive mixed suite.

API tests

  • Playwright's request fixture is enough. APIRequestContext gives cookies, proxy handling and the CA bundle for free, and shares the trace viewer — an API call from a UI test appears in the same trace as the clicks around it, which is worth a great deal during triage.
  • Two base URLs, both from the profile. baseURL and apiBaseURL, resolved in section 04, never assembled by string concatenation in a client.
  • Authenticate by token, not by driving a login. API tests take a token from the secrets fixture or reuse the storage state produced by the setup project. They must not be the reason a login form gets exercised four hundred times.
  • Everything created gets cleaned up. API setup is fast enough to be used everywhere, which means it generates data at a rate UI tests never did. Tag created records with the run id and delete in fixture teardown; a test environment that fills with orphaned records becomes slow and then untrustworthy.
  • Retry policy differs. A UI test that passes on retry is flaky. An API test that passes on retry may be hiding a genuine intermittent 500, so the retried-and-passed signal should be surfaced rather than swallowed — see the first-run-outcome rule in section 18.

Contract testing — one yes and one no

No: consumer-driven contract testing from this repository

Refused

Pact and its relatives work because the consumer writes its expectations, publishes them to a broker, and the provider verifies them in the provider's own pipeline. A test automation repository is not the consumer of anything. A pact written here encodes what the QA team believes the front end needs, which is a plausible fiction, and it would be verified against a running environment rather than at build time — losing the entire point, which is failing the provider's build before deployment.

If the organisation wants thisIt is a development-team initiative needing a broker, changes in each service's pipeline, and consumer tests written by the people who own the consumer. Worth advocating for; not worth absorbing into this plan, where it would be a worse version of a good idea.

Yes: schema conformance, as a cross-cutting check

Adopted

If the services publish an OpenAPI or JSON Schema, every response this framework receives can be validated against it. The design decision worth making early is to run that validation inside the shared API client rather than as a separate suite, so every API call in every test — including the setup calls inside UI tests — is a contract check for free. Roughly a hundred lines with Ajv, and it turns incidental traffic into coverage.

Plus a deliberate passA small contract project that walks each documented endpoint with representative requests, so coverage is by endpoint rather than by whatever the tests happened to call. Validation failures are their own reported category — contract drift, not application defect — because the distinction routes the ticket to a different team.

The dependency is real: this needs a current, published spec. Where none exists, the honest fallback is golden-response snapshots — record a response shape, diff future ones, review changes — which catches drift but cannot say whether the drift was agreed. Worth stating as materially weaker rather than presenting snapshot diffing as contract testing.

Database checks — permitted, read-only, and last on the list

Direct database assertions are the sharpest tool here and the easiest to misuse. A test that queries the schema is coupled to the schema, so it breaks on refactors that changed no behaviour, and it can assert facts the application would never expose — which is another way of saying it can pass while the product is broken.

The rule is therefore a hierarchy, not a preference: assert through the UI if the user can see it, through the API if a service exposes it, and through the database only when neither does. That last case is real — audit rows, async job output, batch postings, soft deletes — which is why the capability exists at all.

  • Read-only, always. The framework never writes to a database. Test data is created through the API or the UI, so the application's caches, events and derived state stay consistent. A row inserted behind the application's back produces failures that surface three tests later and look like something else entirely.
  • Dynamic credentials from Vault. Vault's database secrets engine issues short-lived read-only credentials per run, which is a better answer than a static test-database password in a KV path — nothing to rotate, nothing to leak, and the lease expires by itself. It does need enabling on the Vault side, so it joins the phase 0 requests in section 11.
  • Named queries only. Parameterised statements in db/ with typed return shapes, exactly like locators: no SQL literal in a spec, enforced by lint. Inline SQL is where injection-shaped mistakes and unreadable tests both come from.
  • Per-worker connections, closed in teardown, and capped. A twenty-worker shard opening a connection each can exhaust a test database's limit and take down the environment for everyone — a failure that will be blamed on the application first.
  • Query results are unredacted data. They go through the same scrubbing as everything else in section 11 before landing in a trace, a report, or a PractiTest attachment.
  • Read replicas if offered. Slightly stale data is usually fine for assertions that already poll, and it keeps the suite off the primary.

Capabilities, extended

All three additions are declared per target, which is what stops "no API tests ran" from being invisible:

The reference target exercises the UI path only, which is a limitation to state out loud rather than discover: the API, contract and database paths cannot be proven against it, and need the real environment from the moment they are built.

What this changes elsewhere

AreaChange
Case managementAPI and mixed tests carry PractiTest IDs like any other case. Contract checks generally do not — they verify a spec, not a scripted case — so the require-case-id lint rule is scoped by project rather than applied globally.

What stays out

Unit tests belong in the application repositories, where they run in seconds against code rather than over a network against a deployed environment. Performance and load testing needs different tooling and a different environment. Both get asked for once a framework demonstrably works; the answer to both is no, with a reason.

The case author gets no browser, deliberately

This is the decision in Track A most likely to be argued with, and it is the one worth defending hardest. Give the case-authoring model access to the running application — through the MCP or the CLI — and it will write cases that describe what the application currently does. Those cases pass on day one, pass on a broken build, and can never catch a regression, because the behaviour under test is the oracle they were derived from.

So the roles stay separated by what each one is allowed to see:

Coverage is the guard against invention

The failure mode of a model asked to write test cases from a thin story is not silence — it is fluent, plausible cases for behaviour nobody ever specified. Two mechanical checks contain it:

  • Every case cites an acceptance criterion, and quotes it. coversAC plus acQuoted are required fields, and the quote is verified as a substring of the source story. A case that cannot cite one is not rejected — it is written to a speculative: block that a human triages separately. Some of those will be genuinely valuable edge cases; they should just never enter PractiTest unexamined.
  • Every acceptance criterion maps to at least one case. The inverse check is the more useful one in practice, because uncovered AC is the thing a human reviewer cannot spot by reading a list of cases that all look reasonable. The tool prints the matrix and fails on gaps.

Where acceptance criteria live is an open question per Jira project — a custom field, a heading in the description, or nowhere at all. The extractor is told which field by configuration, and a story with no identifiable AC is rejected at step A2 with that as the stated reason. Generating cases from a title and a paragraph of context is exactly how invention happens.

Git is the staging area; PractiTest is publication

Nothing the model writes goes straight into the test management system. Cases land in cases/<target>/*.yaml, on a branch, and are reviewed as a diff. This is worth the extra hop for three reasons: review-by-diff is a skill the team already has, rejected cases leave a trace of why, and a bad generation run is reverted with git revert rather than by deleting records from PractiTest by hand.

Publication then has to be idempotent, because A6 will be re-run — on an edited story, after a partial failure, or by someone who forgot they already ran it:

  • Identity is the case's slug plus story key, stored in a PractiTest custom field. Re-publishing updates that case; it does not create a second one.
  • Human edits win permanently. If a case's PractiTest updatedBy is a person rather than the service account, the publisher stops touching it and reports it as human-owned. Otherwise a well-meaning re-run silently reverts a tester's correction, which is the fastest possible way to lose the team's trust in this pipeline.
  • Provenance is a field, not a convention. source=ai-authored, the model identity, and the story content hash go into custom fields so AI-authored cases are filterable, auditable, and countable. If the answer to "how many of our cases were written by a model?" is unanswerable, this feature should not ship.
  • Dry run by default. push-cases --dry-run prints what it would create or update. Writing to a shared case repository is the one irreversible thing in this pipeline.

Track B, and the model's smaller job there

pull-cases fetches PractiTest cases into the same cases/*.yaml format. The model's role here is narrower and safer: turn prose steps into the structured schema, and score the case against the quality gate in section 10. It adds no requirements — where the case is ambiguous it marks the ambiguity rather than resolving it, and that becomes the feedback sent back to the case author.

Both tracks then hand the same artifact to the same generator. Anything that improves generation improves both, and there is exactly one place where a case becomes a spec.

Traceability runs both ways, and both hops are hashed

Jira story ──contentHash──▶ PractiTest case ──contentHash──▶ spec annotation
  FIN-2210                      #5104                     tests/…/SD-012.spec.ts

Each artifact stores a hash of the one upstream, and a CI check flags anything whose upstream changed. An edited story surfaces as "3 cases derived from FIN-2210 are stale"; an edited case surfaces as "the spec for #5104 tests a previous version". Without this, Track A quietly makes the drift problem worse than Track B ever did — it adds a second hop for a requirement to change behind code that claims to verify it.

Results go back the same way

Both tracks report identically: the reporter in section 14 posts run results against the PractiTest case ID carried in the spec's annotation, whether that case was written by a person or published by A6. Track A adds one optional extra — a comment on the originating Jira story linking the run — which is what makes the loop visible to the people who wrote the story and will never open PractiTest.

Section 10Test case → running script

The shared spine. Everything below runs identically whether the case arrived from Track A or Track B — which is the point of having one case format.

  1. 01PullCase from cases/*.yaml
  2. 02GateReject cases too vague to automate
  3. 03ExplorePlaywright CLI walks the live flow
  4. 04GenerateGenerator agent writes the spec
  5. 05Verifylint + tsc + run until green
  6. 06ReviewHuman PR review, always
  7. 07ReportRuns to PractiTest, defects to Jira

Two generation modes

Explore-first (default). The planner drives the running application through the Playwright CLI at the profile's baseURL, snapshots the accessibility tree to disk, and generates against observed structure. Slower and it needs a working environment, but locators are real. Against the reference target this mode always works, which is what makes it the phase 2 baseline.

Spec-only (fallback). Generate from case text alone when no environment is available. Output is treated as a draft skeleton and marked test.fixme until it has been run against the app. Being explicit that this mode produces unverified code prevents a quiet flood of plausible-looking dead tests.

The quality gate is not optional

"Automatically create scripts just by looking at test cases" holds only for cases that are actually specific. A case reading "Verify the report is correct" cannot be automated by a human either. Step 02 scores each case on preconditions, concrete input data, an explicit expected result, and a defined starting state, and routes failures back to the case author with the specific gap named.

Expect this to reject a meaningful share of an existing legacy suite on first run. That is the system working — and it is worth saying out loud before anyone reads the rejection report as a tooling failure.

The gate applies to both tracks, and the asymmetry is instructive. A Track B rejection is a message to a human case author with a lead time measured in days. A Track A rejection can loop straight back into step A3 with the gap named — but only once, and the second failure escalates to a person. A model that keeps rewriting a case until it satisfies a specificity checker will eventually satisfy it by inventing the missing specifics.

The healer, on a leash

Auto-healing is the most dangerous capability here: a healer that "fixes" a test to match newly-broken behaviour destroys the test's reason for existing. Constraints:

  • Healing runs in its own workflow and opens a pull request. It never pushes to a protected branch.
  • Locator and timing repairs only. A changed assertion or expected value is escalated to a human, never healed.
  • Every healed test is labelled with what changed, so review is a diff read rather than an act of faith.

Section 11Vault

Authentication

  • CI: JWT/OIDC via GitLab id_tokens — see section 16. This supersedes AppRole and removes the bootstrap-credential problem entirely.
  • Local: OIDC against the corporate IdP, falling back to AppRole or a short-lived dev token. Developers never hold a long-lived credential.
  • Tokens are renewed in-process for long shards and revoked in teardown.

Path layout

KV v2 nests payloads under data.data; the adapter normalises this so callers never see the envelope. Secrets are fetched once per worker, cached in memory, and exposed only through the secrets fixture — never written to disk, never copied into process.env.

Leak control

This is the part that gets skipped and then bites. Playwright traces capture network payloads, screenshots and DOM; a login trace attached to a PractiTest run is a credential in a test management system. Mitigations: register secret values with a redaction helper at fetch time, scrub traces before attaching, keep storageState out of git and out of long-lived artifacts, and add a CI grep for known secret shapes over everything about to be uploaded.

Section 12MFA and OTP

One interface, two providers, and one race condition that will otherwise cost a week of intermittent failures.

interface OtpProvider {
  /** Watermark before the code is triggered. */
  arm(): Promise<Watermark>;
  /** Resolve a code produced after the watermark. */
  get(mark: Watermark): Promise<string>;
}

TOTP via Vault

Vault's TOTP secrets engine acts as the authenticator app: seeds are stored write-only and GET /v1/totp/code/<name> returns a current code. The seed never reaches the test process, which is a real security improvement over the usual pattern of pasting seeds into CI variables.

One sharp edge: if a code is fetched with two seconds left in its window, it expires between fetch and submit. The provider checks remaining validity and waits for the next window rather than returning a code about to die.

Email OTP via the mock inbox

The failure everyone hits: trigger the send, poll the inbox, read the newest message — and get the previous test's code. Hence arm(). Record the inbox high-water mark before triggering, then accept only messages newer than it. Combine with per-worker plus-addressing (qa+<runId>-<worker>@…) so parallel workers cannot read each other's mail, and consume the message once read.

Polling uses expect.poll with a bounded timeout so a missing email fails as a clear assertion rather than a hung test.

The mock SMTP server here is an in-house tool, so the design cannot assume a known API. The adapter must be written against whatever it exposes, and the OTP flow needs four capabilities — the first three are hard requirements:

Section 13Identity, sessions and account lifecycle

Three coupled mechanisms: never log in through the UI unless the test is about logging in, lease accounts from a pool rather than sharing them, and rotate passwords on a schedule without breaking either of the first two.

Storage state is the default; UI login is the exception

Driving a login form before every test is slow, and worse, it makes every test in the suite fail when login breaks — one defect, four hundred red results, and a triage report that tells you nothing. Authenticate once per role, reuse the session everywhere else.

Playwright's setup-project pattern is the right mechanism: a setup project authenticates each required role and writes a storage state file, and the test projects declare dependencies on it so they cannot start before it succeeds.

// playwright.config.ts — one setup project per role
projects: [
  { name: 'setup:auth', testMatch: /auth\.setup\.ts/ },
  {
    name: 'regression',
    dependencies: ['setup:auth'],
    use: { storageState: '.auth/${role}.json' },   // resolved per worker
  },
  {
    name: 'auth-flows',            // the exception
    testMatch: /login|mfa|password/,
    use: { storageState: undefined },              // must start signed out
  },
]

Making that exception explicit as its own project — rather than leaving it to each test to remember — means a spec cannot accidentally inherit a session it was supposed to establish itself. Enforce it with a lint rule: any spec tagged @auth must run in the auth-flows project.

Storage state is a credential

A storage state file contains live session tokens. Anyone who obtains it is signed in as that account, no password or MFA required. So it inherits every rule from section 11: written only to a gitignored .auth/ directory, never uploaded as a CI artifact, never attached to a PractiTest run, deleted in teardown, and regenerated per pipeline run rather than cached across days. Short-lived is the point — a stale session file is both a security exposure and a source of confusing mid-run failures when the server expires it.

Account pools, leased per worker

Accounts come from Vault organised by type and role, and tests declare what they need rather than naming a user:

kv/data/qa/<env>/pools/<accountType>/<role>/<n>
   → { username, passwordRef, mfaSeedRef, rotatedAt, state }

A worker-scoped fixture leases an account for the life of the worker and releases it at teardown. Worker-scoped rather than test-scoped matters: it means one login and one storage state per worker, not per test, while still guaranteeing two parallel workers never share an identity.

  • Leasing must be atomic. Two runners starting simultaneously will otherwise both take account 1. A Vault CAS write, or a small lease record with a TTL, prevents it. Without this, parallel runs corrupt each other in ways that look exactly like flaky tests.
  • Pool exhaustion needs a real error. "No available account for role approver: pool size 4, all leased" — not a timeout ten minutes later.
  • Leases must expire. A crashed runner that never releases its lease will otherwise shrink the pool permanently.
  • Size pools against worker count. Pool size must be at least the maximum concurrent workers per role, or the suite serialises on account availability and nobody understands why it got slow.
  • Mutating tests need their own accounts. A test that changes a user's profile or permissions should lease from a pool marked disposable, not from the shared read-only pool.

Scheduled password rotation

Rotation is a scheduled GitLab pipeline, not something the test run does. Interval is configuration, per environment and per account type:

rotation:
  enabled: true
  maxAgeDays: 60            # per account type, overridable per role
  jitterDays: 5             # avoid rotating the whole pool at once
  blackout: { start: '18:00', end: '06:00' }   # never during the nightly run
  onFailure: quarantine     # remove from pool, alert, do not retry blindly

The order of operations is what makes this safe. Change the password in the application first, verify a login succeeds with the new one, and only then write it to Vault. Writing to Vault first and failing the application change leaves an account nobody can use and a credential store that lies about it.

  1. Acquire an exclusive lease on the account, so no run can pick it up mid-rotation.
  2. Change the password in the application through its own API or UI flow.
  3. Verify by authenticating with the new password.
  4. Write the new value to Vault as a new KV v2 version — the version history is your rollback.
  5. Invalidate any cached storage state for that account.
  6. Release the lease.
  7. On failure at any step: mark the account quarantined, remove it from the pool, and alert. Never leave it in a state where the next run finds it broken.

The blackout window matters more than it looks. Rotating an account while the nightly suite is mid-flight produces authentication failures that look like application defects and will consume a morning of triage. Jitter matters for the same reason at pool scale — rotating every account on day 60 means one night where everything is briefly invalid.

Two smaller points that prevent recurring pain: many enterprise applications enforce password history and minimum-age rules, so the generator must produce values that satisfy the real policy and rotation cannot run more often than the minimum age allows. And if the application forces a change-password screen on first login after a reset, that interstitial has to be handled in the rotation flow, or every subsequent storage state capture silently lands on the wrong page.

The write direction — publishing cases

New in this draft, and the part that changes PractiTest's role. It was a source; it is now also a destination, which brings three requirements the results path never had:

  • Use a dedicated service account, not a person's token. Every AI-authored case will be attributed to whoever's PAT is configured.   • Custom fields must exist before the first publish. source, authoredBy, storyKey and contentHash are how provenance and idempotency work, and creating custom fields is a PractiTest administrator action. Deletion is not in scope in either direction. If a published case turns out to be wrong, a human retires it in PractiTest — an automation that can create cases and delete them is a considerably larger conversation with whoever owns that system.

PAT lifecycle

Jira DC PATs take an optional expiry, and administrators can enforce a maximum lifetime or forbid non-expiring tokens via system properties. Two consequences worth designing for now rather than discovering at 2am:

  • A token that silently expires turns every nightly run's reporting step into a 401. The Jira client should treat 401 as a distinct, loudly-reported condition — "credential expired or revoked" — not fold it into generic request failure.
  • Store the PAT in Vault, not in CI variables. Rotation then means updating one Vault path rather than hunting through pipeline configuration, and the audit trail comes free.
  • Use a dedicated service account, not a person's PAT. Personal tokens inherit that person's permissions and die when they change role or leave.

Integration behaviour

  • Inbound — traceability: a spec's jira annotation links it to the story or defect it covers, giving traceability in both directions.
  • Inbound — story text: Track A's pull-story reads the story, its acceptance-criteria field, and its linked issues, normalising wiki markup to plain text before the case author ever sees it. Which field holds acceptance criteria is per-project configuration, and a story that has none is rejected rather than guessed at. This is a read of a single issue, not a JQL sweep — keeping it narrow keeps the governance conversation in section 17 narrow too.
  • Outbound — run links: optionally, a comment on the story when a run covering it completes. Off by default, one comment per story per run, and never per test — a story with forty linked cases must not accumulate forty comments a night.
  • Outbound: on failure, create or update a defect. Deduplicate on a fingerprint of test ID plus normalised error, so a flaky test produces one ticket with a failure count, not forty tickets.
  • Reopen, don't duplicate: if a matching closed defect exists, reopen with a comment linking the new run. Note that DC transitions are workflow-specific — the adapter must look up available transitions by name rather than hard-coding IDs, which differ per project.
  • Guard rail: defect creation is off by default and enabled per-pipeline. An automated defect filer pointed at a broken environment can create hundreds of tickets in one night.
  • Formatting: descriptions are built as wiki markup. Reusing a Cloud ADF payload here produces tickets displaying raw JSON.

The conversational access that was lost

Losing the official MCP means agents can no longer be asked "what's the acceptance criteria on FIN-2210?" during generation. Two ways to recover part of it:

  • A read-only Jira CLI (jira:issue <key>) that prints an issue as markdown. Cheap, fully under your control, and enough for the generation workflow's actual need — pulling acceptance criteria into context.
  • A community MCP server. sooperset/mcp-atlassian supports Jira Server/DC 8.14+ with PAT auth and is actively maintained. Revised recommendation given the environment: assume this will not clear security review. Handing a third-party package a PAT against an internal, self-hosted Jira is a supply-chain question your security team will reasonably say no to, and it is not worth spending review capital on a convenience feature.

Recommendation: build the CLI, and only the CLI. The reporter needs the REST client anyway, so the CLI is a thin wrapper over code you are writing regardless — no new dependency, no new egress path, no review. Track A raises its value further: pull-story and the CLI are the same code path, so the conversational convenience and the authoring pipeline are one thing to build and one thing to maintain.

Section 16GitLab CI

GitLab changes three decisions from earlier drafts, all in the plan's favour — it removes the AppRole bootstrap problem, it answers the report-hosting question, and it puts results on the merge request.

Vault authentication via OIDC, not AppRole

This supersedes the AppRole recommendation in section 11 for CI. GitLab issues a signed JWT per job through the id_tokens keyword, Vault validates it against your GitLab's OIDC discovery URL, and the secrets keyword uses it automatically. There is no secret_id to deliver, wrap, or rotate — the bootstrap credential problem disappears.

.vault-auth:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.<internal>
  secrets:
    PRACTITEST_TOKEN:
      vault: qa/shared/integrations/practitest@kv
    JIRA_PAT:
      vault: qa/shared/integrations/jira@kv

The real advantage is bound claims. A Vault role can require project_path and ref to match, so a job on a feature branch of a forked project cannot read staging credentials even with a valid token. That is meaningfully stronger than AppRole, where possession of the secret ID is the whole authorisation. Keep AppRole only for local developer runs outside GitLab.

Your Vault is a separate system — what that changes

It does not break this design; a separately-operated Vault is the normal topology for JWT auth. But it makes two prerequisites explicit, and both belong to a different team than the one building this framework.

  • Someone must enable and configure the JWT auth backend on Vault, create the role, and set the bound claims. This is a Vault administrator task with its own request process. Nothing in the pipeline works until it is done, so raise it in phase 0.
  • Vault must be able to validate GitLab's token signature, and there are two ways to arrange that. oidc_discovery_url has Vault fetch GitLab's keys at authentication time — clean, self-maintaining, but it requires Vault to reach GitLab over the network, which across security zones is not a given.

If that path is blocked, the fallback is jwt_validation_pubkeys: GitLab's signing public keys are configured directly into the Vault backend, and no network call is made. The three options — oidc_discovery_url, jwks_url and jwt_validation_pubkeys — are mutually exclusive, so this is a deliberate choice, not a layered fallback.

The trade-off is real and worth stating to whoever configures it: static public keys remove the network dependency but also remove automatic key rotation. When GitLab rotates its signing key, every pipeline fails authentication until someone updates Vault by hand. Prefer discovery if the network path can be opened; choose static keys knowingly, with a documented owner, if it cannot.

Confirm the direction of reachability too. OIDC discovery needs Vault → GitLab, while the runner needs GitLab runner → Vault. These are separate firewall rules and it is common for one to exist without the other.

Section 18The run report

Serenity's real achievement is not that it is pretty. It is that a product owner can read it without knowing what a locator is. That is the property worth copying — and it is orthogonal to visual polish.

One data model, three renderings

The mistake to avoid is generating HTML directly from the reporter. Everything downstream — the report, the email, the PractiTest push, the triage agent — needs the same facts, and each one re-deriving them from Playwright's raw output guarantees they eventually disagree. So the reporter's only job is to emit a normalised, versioned run-result.json; every consumer reads that.

  1. Sourcerun-result.jsonCanonical, versioned, shard-merged
  2. Render ARich HTMLSelf-contained, browser, full evidence
  3. Render BEmail digestOutlook-safe, ~600px, links out
  4. Render CPractiTest + JiraRuns, defects, attachments

A useful side effect: the report becomes testable. Feed a fixture run-result.json with a known mix of pass, fail, flaky and skipped, and assert the rendered HTML. Reports that are generated only from live runs are never tested and quietly rot.

What "comprehensive" should actually contain

Ordered by how often someone genuinely needs it — not by what is easy to compute.

Two of these are the ones teams skip and later wish they had. Flake rate as a rate, not a count — a test that fails 1 in 3 runs matters far more than one that failed twice ever. And first-run outcome recorded separately from final outcome, because a suite that is green only after retries is not green, and the distinction disappears if you record only the final state.

Getting flaky right in the reporter

A detail that produces wrong numbers if missed: onTestEnd fires once per attempt, including every retry, so counting statuses there double-counts retried tests. Flakiness is only knowable once all attempts are done. Aggregate in onEnd using test.outcome(), which returns expected, unexpected, flaky or skipped — that is the API that actually encodes "passed, but not first time".

The Serenity qualities worth carrying over

  • Narrative steps in business language. Playwright's test.step() titles become the report's narrative, so step naming stops being cosmetic and becomes the report's readability. This should be a lint-enforced convention: steps are named for intent, not mechanics — "Submit the expense claim", never "click #submit-btn".
  • Evidence attached to the step, not the test. A screenshot at the failing step is worth ten at the end. Capture per step on failure paths.
  • Requirements coverage as a first-class view. With PractiTest IDs on every spec, the report can show set coverage directly — the closest thing to Serenity's living documentation available here, and more valuable than any visual flourish. Track A's coversAC field extends it one hop further: coverage stated against acceptance criteria, not just against cases, which is the number a product owner actually wanted all along.
  • Readable without the code. The test is the disclosure, not the source file. Every failure states what was expected in plain language before it shows a stack trace.

Build it, or theme Allure?

Worth deciding deliberately rather than by default. Allure is the most capable off-the-shelf option — history, trends, categories, step detail, attachments — and adopting it costs days rather than weeks. What it does not give you is a PractiTest coverage view, the triage verdict column, or your own visual identity, and its categories mechanism is regex-over-error-text rather than genuine analysis.

Recommendation: emit run-result.json plus Allure results from the same reporter. Use Allure immediately for deep per-test forensics, and build the bespoke report as the executive and stakeholder view fed by the same JSON. They serve different readers, the duplication is small, and it avoids a month of rebuilding trend charts that already exist.

The report's visual spec

Self-contained single HTML file — inlined CSS and JS, evidence embedded or referenced by relative path, no CDN. It must open from a file share with no server. Structure: a status band that reads correct at a glance from across a desk, a triage summary, filter chips (status, suite, category, owner, "new only"), a virtualised results table for suites in the thousands, and an expandable evidence drawer per test rather than a separate page. Semantic colour for pass/fail/flaky/quarantined is a data encoding here, kept distinct from the brand accent, and never the only signal — pair it with shape or label for accessibility.

Section 19Delivery by email

The instinct is to email the pretty report. That does not work, and knowing why up front saves building something twice.

The constraint

Outlook desktop renders HTML through the Word engine: no flexbox, no grid, no CSS custom properties, no media queries, no reliable border-radius, no background images. Microsoft has said it will retire Word-based rendering in favour of the Chromium engine, but an enterprise on managed desktops will be behind that curve for a long time. Two further traps:

  • Base64 data: images do not work. Gmail strips them; Outlook blocks them outright. Inline images must be CID attachments — which Nodemailer supports natively — or hosted on an internal server and linked.
  • An .html attachment will probably be quarantined. HTML attachments are a standard phishing vector and corporate mail filters routinely strip them. Do not make the rich report an attachment.

The design that survives this

  1. Publish the rich report to the CI artifact store or an internal web server, at a stable per-run URL.
  2. Email a digest, not the report. Table-based layout, ~600px, fully inlined CSS, no JavaScript, a plain-text alternative part for accessibility and filters. It carries the verdict band, the counts, the triage summary, and the top failures — enough that someone can decide whether to open anything at all.
  3. Link out for everything else. One prominent "Open full report" bulletproof button (VML-wrapped so Outlook renders it), plus deep links per failing test.
  4. Degrade to inline detail only if hosting is unavailable. If nothing can host the report, expand the digest to include the top failures' errors as text. Never attach the HTML.

Nodemailer specifics

  • SMTP credentials come from Vault via the same secrets fixture, never from CI variables.
  • Set both html and text. Some corporate gateways score HTML-only mail as spam.
  • Inline images as attachments with a cid: reference. Keep them few and small — a status band and a trend sparkline, not screenshots.
  • Send once, from the merge job, after all shards report. Per-shard emails are how a team learns to filter your notifications into a folder they never open.
  • Subject line carries the verdict, not the tool: [FAIL] Regression · staging · 12 failed, 4 flaky · build 4821. It should be triageable from a phone lock screen.
  • Failure to send must not fail the build — log, retain the digest as an artifact, and move on.

Section 20The failure triage agent

The most valuable component in this plan, and the one most likely to be built wrong — because the obvious implementation is to hand every failure to a model and ask what happened.

Two passes before any AI runs

Pass 1 — cluster. Group failures by signature: normalised error, failing step, and time window. If forty tests fail with the same connection error in the same two minutes, that is one environment incident, not forty defects. Triage the cluster once.

This single decision does three things at once: it stops forty Jira tickets being filed on a bad night, it cuts triage cost by roughly the clustering factor, and it makes the answer more accurate — because breadth is itself the evidence for an infrastructure cause, and a per-test view cannot see it.

Pass 2 — classify by rule. A large share of failures are deterministically identifiable and need no model at all:

What the agent is given, and what it must return

Evidence: the normalised error and stack, the failing test.step() and the steps that preceded it, the DOM snapshot at failure, the network log with status codes, console errors, before/after screenshots, retry history, this test's failure history, what else failed in the same window, the commits deployed since the last green run, and the case's provenance — who authored it, which acceptance criterion it claims to cover, and the criterion's text. That last item is what makes the case defect category decidable rather than guessed at: a failure where the application matches the quoted criterion and the assertion does not is a case defect, and no other evidence establishes that.

Output is a strict JSON contract, validated on receipt — free-text findings cannot be aggregated, filtered, or trended:

{
  "clusterId": "c7f2",
  "category": "application-defect",
  "confidence": "high",              // high | medium | low — never a fake percentage
  "summary": "Approval limit not enforced for amounts over 10,000",
  "evidence": [
    "POST /api/claims returned 201 for amount=15000",
    "No validation error rendered; assertion expected 'exceeds limit'",
    "Same behaviour on both retries — not timing-related"
  ],
  "affectedTests": ["TC-4821", "TC-4822"],
  "recommendedAction": "file-defect",  // file-defect | heal | fix-test | fix-data | escalate | none
  "suggestedOwner": "payments-team",
  "needsHumanReview": false
}

Guardrails

  • Advisory by default. The agent annotates the report. Filing a Jira defect stays behind the same per-pipeline switch as section 15, and auto-filing should stay off until the category accuracy has been measured over several weeks.
  • Every claim cites evidence. A verdict without a specific artifact reference is rejected by the schema validator. This is what makes the output reviewable rather than merely confident-sounding.
  • Three confidence levels, not percentages. A model's "92% confident" is not a calibrated probability, and printing it as one manufactures trust the number cannot support.
  • Low confidence is a valid answer. needsHumanReview routes it to a person unclassified. An agent that always produces a category will produce wrong categories.
  • Triage never heals. It may recommend heal; the healer's own constraints from section 10 still apply, and a human still reviews the PR.
  • Traces carry application data. Sending them to a model is the same governance question as section 17 — scrub before sending, and only from non-production environments.

Measuring whether it works

A triage agent nobody trusts is worse than none, because it adds a step without removing one. So instrument it: record the agent's category alongside the human's eventual verdict, and report agreement rate per category monthly. Expect it to be genuinely good at network, environment and dependency — where evidence is unambiguous — and weakest at distinguishing application defect from test logic defect, which needs requirement context it may not have. Publishing that breakdown is what earns the team's trust in the categories that are reliable.

Section 22Self-critique

Written adversarially against the plan above. Severity reflects how much of the design has to change if the concern proves out.

An AI-authored case can invent a requirement, and then it has authority

High

New with Track A, and the sharpest risk in this draft. A model given a thin story does not produce nothing — it produces fluent, well-formatted cases for behaviour nobody specified. Once such a case is published to PractiTest it stops looking like a model's guess and starts looking like a requirement: it appears in coverage numbers, a spec gets written against it, and eventually someone files a defect because the application does not do a thing it was never asked to do. The formatting is what makes this dangerous — invented cases are indistinguishable from real ones by inspection.

ResponseMandatory coversAC with the criterion quoted verbatim and verified as a substring; uncited cases quarantined as speculative rather than published; the git approval gate so nothing reaches PractiTest unreviewed; source=ai-authored as a queryable field; and the blind-review baseline in phase 4b measuring invention rate explicitly rather than hoping it is low. If invention rate is not measured, Track A should not run unattended.

An e2e suite that accepts API tests becomes where all tests go to live

High

New with section 05, and the most predictable consequence of it. Once this repository can make HTTP calls and read a database, it becomes the path of least resistance for every test anyone wants written — including the ones that belong in a service's own unit or integration suite, where they would run in two seconds against code instead of two minutes against a deployed environment. The pyramid inverts one reasonable-sounding request at a time, and the first symptom is a nightly run that takes four hours and nobody can explain why.

ResponseA written admission rule, applied at review: a test earns a place here only if it crosses a boundary the owning team's tests cannot cross — UI to service, service to service, or a real deployed environment. Anything provable inside one codebase gets sent back with that reason. Track suite duration and test count per kind in the report from phase 2b so inversion is visible as a trend rather than as a crisis, and treat the merge-request budget as a hard limit that new tests must fit inside.

Database assertions couple the suite to a schema nobody told you changed

Medium

A query against a table is a dependency on a private implementation detail with no contract and no deprecation notice. The application team renames a column in a routine refactor, the nightly suite goes red, and the report says the product is broken when nothing is. Worse in the other direction: a DB assertion can pass while the feature is broken for users, because it verifies a row rather than an outcome anyone experiences.

ResponseThe hierarchy in section 05 is the control — UI, then API, then database, and only for facts nothing else exposes. Keep the count small and reviewable, name each query for the business fact it establishes rather than the table it reads, and tell the owning team which columns the suite depends on. If that list is too long to send, it is too long.

Contract checking will be asked to become Pact

Low

"We already do contract testing" is a comfortable thing to say, and schema conformance is not what most people mean by it. The risk is not the technique, which is genuinely useful — it is the claim, which could let a real consumer-driven initiative be deferred on the grounds that it is already covered.

ResponseName it precisely in the report and in conversation: schema conformance, which catches provider drift after deployment. Say explicitly what it does not do — fail a provider's build before release — and keep advocating for the real thing in the teams that own the services.

A demo site is not a proving ground

High

Everything genuinely hard in this plan is invisible on saucedemo. It has no MFA, so section 12 is untested. It has fixed public users, so the pool, leasing and rotation work in section 13 — the most dangerous automation here — never executes. Its DOM does not change, so the healer has nothing to heal and locator drift never occurs. And it has no API, no schema and no database, so the entire second half of section 05 has no way to be exercised there at all. A suite that is green against it demonstrates that the wiring works and almost nothing else, and a green dashboard is exactly the artifact that stops people asking harder questions.

ResponseName its role precisely and hold to it: reference target for wiring, MR smoke, generation baseline and triage ground truth — never evidence that the design is sound. Every phase exit that involves Vault, MFA, pools or rotation must be met against the real target. Where the reference target cannot produce a condition, build a harness rather than skipping it: the drift harness in phase 7 exists for this reason.

PractiTest is now both source of truth and downstream system

Medium

The clean story — PractiTest is the source, code follows it — becomes circular once Track A writes cases into it. Two writers now edit the same records: a pipeline and a team of testers. The predictable failure is a re-run silently reverting a tester's correction, and the predictable second-order effect is that testers stop correcting cases because they do not trust the changes to survive.

ResponseAn explicit ownership rule, enforced in code rather than documented: a case whose last editor is a human is human-owned from that moment and the publisher will not touch it, reporting it as skipped instead. Plus idempotent identity, dry-run by default, no delete capability in either direction, and provenance fields so the split between authored-by-pipeline and authored-by-person is always countable. Tell the PractiTest owners this automation exists before it first runs, not after.

Story → case → spec is a three-hop game of telephone

Medium

Track B has one lossy hop, from case to code, and a human reads the case. Track A adds a second, from requirement to case, and each hop's output becomes the next hop's ground truth. A misread acceptance criterion becomes a confidently wrong case, which becomes a confidently wrong test that passes — and a passing test is never investigated. Compounding error in a pipeline whose every stage sounds plausible is hard to detect from any single artifact.

ResponseThe human gate sits between hop one and hop two precisely because that is the only hop where the error is still cheap to catch. The verbatim AC quote travels with the case so a reviewer compares against the requirement rather than against their memory of it, and content hashes make either hop's drift visible. It is also worth accepting that Track A suits new, well-specified stories and suits legacy work badly — that is a scoping decision, not a tooling gap.

The headline promise is oversold

High

"Automatically create scripts just by looking at test cases" implies a hands-off pipeline. Realistically, explore-first generation against a well-written case produces a spec needing minor review most of the time; against a typical legacy case it produces something needing real work. The quality gate in section 10 mitigates but does not remove this. Track A extends the same promise one hop earlier, where the honest version is "drafts cases a human still has to agree to".

ResponsePhase 2 measures the hit rate on real cases before anyone commits to a target. Frame the deliverable as "drafts a reviewable spec" rather than "writes the test", and let the measured number set expectations.

Six integrations at once is the classic way this dies

High

Playwright, MCP, Vault, mock SMTP, Jira, PractiTest, plus API clients, schema validation, database access, a novel framework shape, two authoring tracks and three distinct AI roles. Any one of them can absorb a week. Built in parallel, nothing is demonstrable for two months and the first integration problem stalls everything.

ResponseThe phasing is explicitly a walking skeleton, and every phase has a demonstrable exit criterion. The reference target improves this materially — phases 0 to 2 now depend on no external system at all, so the first demonstrable thing arrives before any firewall request is answered. If the plan is adopted, the phase boundaries should be treated as hard, and Track A stays in phase 4b rather than being pulled forward because it demos well.

The four-layer split is a bet, not a proven pattern

Medium

The argument that a closed vocabulary beats POM for generation is reasoned, not measured. Models have seen enormous quantities of POM in training and comparatively little of this shape, so priors may partly work against it. It is also more structure than a small suite needs.

ResponseFalsifiable in phase 2 — generate the same ten cases against both shapes and compare. The layers are conventions plus lint rules, so reverting toward POM is cheap if the data says so.

Traces and attachments are a live credential leak path

High

Doing Vault properly and then base64-ing an unscrubbed trace of a login flow into PractiTest defeats the entire exercise. Scrubbing is easy to specify and easy to implement incompletely — a password typed character by character does not appear as a contiguous string in a DOM snapshot.

ResponseTreat this as a feature with its own test: a deliberate leak test that fails if a known canary value survives into any artifact. Until that test exists, attachments stay off.

The healer can quietly erase regression coverage

Medium

A locator repair and a bug are indistinguishable from inside the test. If the login button's accessible name changes because someone broke the i18n bundle, healing the locator hides a real defect and the suite goes green on a broken build.

ResponsePR-only healing, no assertion changes, labelled diffs. Worth adding: a healer that files a Jira ticket instead of only a PR when it repairs the same locator more than once in a fortnight.

"Vault gets no MCP" will feel obstructive

Medium

The first time someone debugs a credential problem, wanting the agent to just read the secret is entirely natural, and the rule will get quietly broken. Security controls that depend on discipline decay.

ResponseMake the safe path easier than the unsafe one — a vault:check CLI that reports whether a path resolves and what shape it has, without ever printing values. Most debugging needs the existence check, not the secret.

PractiTest rate limits are tighter than they look

Medium

Thirty calls per minute is not much once instance resolution, run creation and attachment uploads are counted, and sharded CI multiplies callers. Naive implementation hits 429s on the first full nightly run.

ResponseThe merge-then-post design in section 14 addresses it, at the cost of no live progress during a run. That trade should be stated to stakeholders who may expect results appearing in real time.

Supporting both AI clients equally doubles the surface that can rot

Medium

Both Copilot Chat and Claude Code are now first-class, which is a real requirement rather than a preference — but generating copilot-instructions.md and CLAUDE.md from one source only keeps the text aligned. Different context windows, tool-calling behaviour and MCP support still produce different code from identical instructions. Two init-agents loops (--loop=vscode and --loop=claude) also means two agent definition sets to keep current.

ResponseAccept the cost, contain it three ways. Lint, types and the test run are the equaliser — whatever writes the code passes identical gates. Run the phase 2 hit-rate experiment separately per client so divergence is measured, not assumed. And add a CI check that both agent definition sets were regenerated against the installed Playwright version, since a stale set fails silently.

Jira Data Center weakens the traceability story

Medium

New in this draft. With no official MCP, agents cannot pull acceptance criteria conversationally while generating, so the requirement context that would improve generated assertions has to be fetched explicitly or pasted by a human. Self-hosted Jira also tends to mean network restrictions — CI may not reach it at all without a firewall exception, which nobody has requested yet.

ResponseThe read-only CLI in section 15 covers the generation-time need at low cost, and Track A's pull-story is the same code path — the acceptance criteria that would have been fetched conversationally are now fetched deliberately and stored, which is better for reproducibility anyway.

And the networkReachability is a genuine unknown, and Track A raises the stakes — it needs Jira from CI, not just from a developer's laptop. Confirm CI-to-Jira reachability during phase 0, not phase 4, because an infrastructure request has a lead time no amount of code can shorten.

Dual source of truth between Jira and PractiTest

Medium

Requirements in Jira, cases in PractiTest, code in git — three systems that will drift. A case updated in PractiTest does not notify the spec; the spec silently tests yesterday's requirement. Track A makes this worse before it makes it better, because it adds a second hop for a requirement to change behind code that claims to verify it.

ResponseHash both hops, not just one: the case stores a hash of the story it came from, the spec stores a hash of the case, and a CI check flags either side going stale. Cheap, and it converts silent drift into a visible task — and it is the one thing Track A adds that also improves Track B, since cases/*.yaml gives the hash somewhere to live.

Password rotation is the most dangerous automation in this plan

High

Everything else fails safe. Rotation writes to a live system, and its failure modes lock accounts out: a password changed in the app but not persisted to Vault, a rotation firing mid-run, an application-enforced history rule silently rejecting the new value, or a forced change-password interstitial that the flow does not expect. In a regulated environment, repeated failed logins against a locked account may also trip security monitoring — which is a conversation nobody wants to have unprepared.

ResponsePhase 1b exists precisely so this is not rushed alongside the pool work. App-first-then-Vault ordering, verify before persist, exclusive lease during rotation, blackout windows, jitter, and quarantine rather than retry. Test it against a disposable pool before it ever touches the shared one, and tell whoever owns account security that this automation exists before it runs.

Cross-team dependencies now sit on the critical path

High

New with the confirmation that Vault is operated separately. Phase 1 cannot complete until a Vault administrator enables the JWT backend and creates a role with bound claims, and OIDC discovery additionally needs a network path from Vault to GitLab that may not exist. None of this is work the QA team can do, estimate, or expedite, and it is the classic cause of a plan that looks on track until it stops entirely.

ResponseRaise both requests in phase 0, before writing the Vault adapter. Keep progress independent of the answer by writing the adapter against its own interface and unit-testing it with an in-process fake — no local Vault instance to stand up, and the fake doubles as the test that the adapter's error handling is correct. Keep the auth method behind that same interface so switching from AppRole to OIDC — or to static public keys — is a configuration change rather than a rewrite.

Both Playwright agent tools are pre-1.0

Medium

@playwright/mcp is at 0.0.79 and @playwright/cli at 0.1.18. The agent definitions are explicitly meant to be regenerated whenever Playwright updates, which means the command surface and generated files this plan describes will move. Building tooling tightly around either is building on a moving foundation.

ResponsePin exact versions and treat upgrades as deliberate, tested changes rather than routine dependency bumps. Keep project-specific logic — case pulling, result pushing, conventions — in your own scripts rather than inside generated agent definitions, so an upgrade regenerates their files and not yours. The CI check for agent-definition freshness exists for exactly this.

The account pool is a shared mutable resource, and those always leak

Medium

Leases assume every holder releases them. Crashed runners, cancelled pipelines and killed jobs do not. Over weeks a pool silently shrinks until the suite serialises or fails on exhaustion, and the symptom — intermittent slowness, then sudden failures — looks nothing like the cause. Tests that mutate their leased account's state compound it.

ResponseTTL every lease so abandonment self-heals, report pool utilisation in the run report so shrinkage is visible before it is critical, and separate disposable pools for mutating tests from read-only shared ones. Treat "pool exhausted" as a first-class error with a named role and count, never a timeout.

A bespoke report is a product, and products need owners

Medium

"Prettier than the Playwright report" sounds like styling; a Serenity-class report is virtualised tables, trend storage, evidence handling and a build pipeline. It will take longer than estimated, and in eighteen months it is either someone's job or it is abandoned at whatever state it reached — and abandoned reporting is worse than the stock report, because people stop trusting it before they stop receiving it.

ResponseThe Allure-in-parallel recommendation is the hedge: if the bespoke report stalls, the team still has capable forensics and nothing is blocked. Keep the bespoke surface deliberately small — executive view, coverage, triage — and resist rebuilding what Allure already does well.

Trend data needs somewhere to live, and nothing owns that yet

Medium

Flake rate, pass-rate trends and "new since last run" all require history, but the plan describes per-run artifacts only. CI artifact retention is typically days to weeks, and it is not a queryable store. Without deciding this, the most valuable band of the report silently degrades to a single run's snapshot.

ResponseDecide it in phase 5, before building the trend views. Cheapest workable option: append each run's summary to a small committed JSON-lines file or an internal object store bucket, keyed by branch and environment. A database is not needed for hundreds of runs a year, and choosing one is how this stalls.

The triage agent's confidence will be over-trusted

High

The genuine risk is not that it is wrong — it will be, sometimes — but that a wrong verdict is stated fluently next to correct ones and is indistinguishable from them. "Test data issue" on what is actually a production-affecting defect is a miss that a plausible explanation actively conceals, and the report's authority makes it worse.

ResponseThree levels rather than percentages, mandatory evidence citations, a valid "needs human review" outcome, no auto-filing, and a published per-category agreement rate. The report should also visually mark AI verdicts as distinct from rule-derived ones, so readers know which is which. Treat any category below a measured agreement threshold as advisory-only in the UI.

Email is a notification channel people learn to ignore

Low

A nightly mail that is green 90% of the time trains its recipients to filter it. The value is in the exceptions, and undifferentiated daily mail destroys the signal — while a corporate mail gateway may also throttle or quarantine a repeating automated sender.

ResponseMake the subject line carry the verdict so it is triageable unopened, and consider sending detail only on failure or change of state, with a weekly summary otherwise. Confirm the sending account is a sanctioned service mailbox rather than a person's.

Generation cost has not been estimated

Low

Explore-first generation is token-expensive: snapshots are large and the verify-repair loop iterates. Across hundreds of cases, plus healer runs, this is a real budget line nobody has priced.

ResponseMeasure cost per generated test during phase 2 alongside the hit rate. It is one extra number from an experiment already planned.

The internal mail tool is the largest remaining unknown

High

Severity raised from the previous draft. An in-house SMTP mock has no documentation I can design against, and the email-OTP flow depends on three specific capabilities it may not have. If it lacks a read API, a whole authentication path is unautomatable until something changes.

ResponseThe capability table in section 12 states exactly what is required and what each gap costs, and the Mailpit-as-sink fallback keeps the plan viable in the worst case. But this is now the top item to resolve before phase 1 starts.

Environment friction is underweighted

Medium

Raised from Low. Windows development host, no Vault CLI — and a restricted internal network on top, meaning proxy, private CA and registry mirror configuration before a single test runs. Line endings, path separators and container networking each cost an afternoon, and none of it appears in the phase estimates.

ResponseSection 17 now enumerates the specific failure modes. HTTP-API-only Vault access avoids the CLI dependency. Enforce LF via .gitattributes from the first commit, and confirm whether CI is Windows or Linux — if they differ, that difference will surface as flakes.

Approval to send context to a cloud model may not exist

High

Potentially fatal to the central premise, and broader in this draft than the last. The generation approach depends on an AI client receiving application snapshots and case content; Track A additionally sends whole Jira stories, which routinely carry more sensitive business context than any UI snapshot does. In a self-hosted, regulated environment that is a data-governance question with a real chance of a restrictive answer — and it is the kind of question that surfaces at phase 3 review, after the framework is built around an assumption nobody validated.

ResponseMove it to phase 0 as a written confirmation, not a corridor conversation, and ask about the three data classes separately — snapshots, case text, story text — because the answer may well be different for each. The design degrades in stages rather than collapsing: a no on story text removes Track A only; a no on snapshots removes explore-first generation; a no on everything still leaves the four-layer shape, Vault, OTP, PractiTest, Jira and the whole reporting and triage-by-rule stack standing. Knowing which of those you are in during week one is worth far more than discovering it in month three.
