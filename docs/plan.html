Section 01The recommendation in one page

Five decisions carry this design. Everything else follows from them.

Not classic POM — a four-layer split

Decision

Locators, actions, fixtures, specs. Page Object Model's open-ended class surface is exactly what makes LLM output drift. A closed vocabulary of typed fixtures and named business actions turns generation into a constrained choice rather than free composition.

Playwright's own agents are the generation engine

Decision

Playwright 1.56+ ships planner, generator and healer agents, installed with npx playwright init-agents --loop=claude|vscode. Do not hand-roll this. Drive them through @playwright/cli rather than the MCP server — roughly 4x fewer tokens for the same work — and wrap them with project skills that pull the test case in and push the result out.

Vault is never an MCP server

Decision

An authoring agent with tool access to Vault can read a live credential and bake it into generated source or a chat transcript. Secrets resolve at runtime, inside the test process, through a fixture. The agent only ever writes the reference, never the value.

Two OTP channels, one interface

Decision

Vault's TOTP secrets engine handles authenticator-app MFA; the mock SMTP inbox handles emailed codes. Both sit behind OtpProvider so a spec says await otp.get() and does not care which.

Reporting is best-effort, never build-blocking

Decision

PractiTest allows 20 instances per run POST and 30 API calls per minute. A custom reporter batches and throttles inside that envelope, and a reporting failure degrades to a warning plus an artifact — it never turns a green suite red.

Section 02What "AI-legible" actually means

The common reading is "write good docs so Copilot understands the repo." That is the weakest version of the idea and it does not survive contact with a 400-test suite.

A model generating a test is doing constrained search. Legibility is whatever shrinks the search space and whatever tells the model, without a human, that it went wrong. Three properties do the work:

1. A small, closed vocabulary

If there are eight fixtures and forty named actions with typed signatures, generation is close to multiple choice. If the model can call any method on any page object, plus raw page.*, it will invent loginPage.loginWithValidCredentials() — plausible, non-existent, and only caught at runtime.

2. Conventions that execute

A markdown rule saying "prefer getByRole" is advisory. An ESLint rule that fails on page.locator('.css-selector') is a feedback signal the agent can act on by itself. Every convention worth having should be expressible as a lint rule, a type, or a failing test. Documentation is the fallback for the rest.

3. Locators grounded in a real snapshot

This is what the Playwright MCP buys. Asked to write a login test from prose alone, a model guesses selectors from its priors. Given a live accessibility snapshot of the actual page, it reads them. Locator hallucination is the single largest source of dead-on-arrival generated tests, and exploration is the only real fix.

Classic POM helps with none of the three. It is a code-reuse pattern from an era when a human wrote every line, and it is being carried forward on momentum.

Section 03Framework shape

Four layers, each with one job and a hard rule about what it may not do.

L1 locators/Flat maps of named locators. getByRole first, then getByLabel, then getByTestId. No logic, no waits, no assertions.
L2 actions/Business verbs — submitExpenseClaim(data), completeMfaChallenge(). Composes L1. Returns data, not page objects. Asserts nothing except its own invariants.
L3 fixtures/The injectable surface: authedPage, secrets, otp, inbox, apiClient, testData. Handles setup, teardown, and worker isolation.
L4 tests/Thin specs, one per managed test case, carrying its PractiTest and Jira identifiers as annotations. All assertions live here.

The rules that make it hold

  • Specs never import from locators/ — if a spec needs an element, the missing thing is an action.
  • Actions never assert outcomes. Assertions in specs keep test intent readable and reviewable, which matters when a human is reviewing generated code at volume.
  • No waitForTimeout, ever. No CSS or XPath without an inline justification comment that lint recognises.
  • A spec body should be readable aloud to a manual tester and match their test case step for step.

What a generated spec looks like

test('TC-4821 · Expense claim rejected above approval limit', {
  annotation: [
    { type: 'practitest', description: '4821' },
    { type: 'jira',       description: 'FIN-2210' },
  ],
}, async ({ authedPage, expenses, testData }) => {
  const claim = testData.expenseClaim({ amount: 15_000 });

  await expenses.submitClaim(authedPage, claim);

  await expect(authedPage.getByRole('alert')).toHaveText(
    /exceeds your approval limit/i,
  );
  await expect(await expenses.statusOf(claim.reference)).toBe('Rejected');
});

Alternatives considered

Section 05The agent contract

Four artifacts that together let any competent coding agent — Copilot Chat, Claude Code, Codex — produce conforming tests without a human explaining the framework each time.

Conventions, written once

docs/CONVENTIONS.md holds the layer rules, the locator priority order, naming, annotation format, and the "never do this" list. tools/sync-instructions.ts renders it into CLAUDE.md, AGENTS.md and .github/copilot-instructions.md with the right front-matter for each client. CI fails if any target is stale.

A generated capability catalog

tools/build-catalog.ts walks the TypeScript AST with ts-morph and emits every exported fixture and action with its signature and doc comment. The agent is instructed to select from this file and to stop and ask if the needed action is absent. This is what stops helper-method hallucination, and it cannot go stale because it is derived from code.

Executable guardrails

RuleEnforced by
No raw CSS/XPath locatorseslint: no-raw-locators
No waitForTimeouteslint: no-hard-waits
Specs may not import locators/eslint: layer-boundaries
No process.env for credentialseslint: secrets-via-fixture
Every spec carries a PractiTest annotationeslint: require-case-id

The loop that matters: agent writes → lint + tsc + playwright run → structured errors → agent repairs. Anything a human has to catch by eye is a convention that has not been finished.

Golden examples

Three reference specs the agent is told to imitate — a simple CRUD flow, an MFA login, and a data-driven case. Few-shot grounding in-repo outperforms prose instructions by a wide margin, and these double as the framework's own smoke tests.

Section 06Agent tooling — CLI over MCP

Reversed from earlier drafts, and the evidence is not close. Playwright now ships a CLI built specifically for coding agents, and for this use case it beats the MCP server on the axis that matters most.

Why the CLI wins here

The two tools differ in where browser state lives. The MCP server streams the accessibility tree, console output and screenshots into the model's context on every action, and it accumulates. @playwright/cli writes snapshots to disk as YAML and lets the agent read what it needs, when it needs it.

Playwright MCPPlaywright CLI
Browser stateStreamed into context every actionWritten to disk, read on demand
Tokens, typical task~114,000~27,000
Long flows (20+ steps)Degrades — stale snapshots accumulateHolds up — context stays clean
Playwright's own guidanceSpecialised agentic loops, explorationCoding agents: Claude Code, Copilot

That token figure is Microsoft's own benchmark for the same task, and the roughly 4x gap compounds across a suite of hundreds of generated tests. Three further reasons it fits this project specifically:

  • It names your exact clients. Playwright's documentation positions the CLI for "coding agents (Claude Code, GitHub Copilot)" — both of which you are supporting as first-class.
  • It is skills-based. playwright-cli install --skills installs agent skills directly, which is what the original brief asked for. This is now a supported path rather than something to hand-roll.
  • Less application data leaves the building. Snapshots on disk that the agent reads selectively means materially less of your app's rendered content streamed to a cloud model than the MCP's stream-everything model — a real advantage against the section 14 governance constraint.

Command surface

npm install -D @playwright/cli@latest
npx playwright-cli install --skills      # agent skills
npx playwright-cli install-browser

npx playwright-cli open <url>            # launch
npx playwright-cli snapshot              # YAML snapshot with element refs
npx playwright-cli click <ref>           # ref-based, deterministic
npx playwright-cli state-save auth.json  # cookies + localStorage
npx playwright-cli state-load auth.json
npx playwright-cli -s=<name> open <url> --persistent   # named session

state-save and state-load are worth noting — the CLI's session handling lines up directly with the storage-state strategy in section 10, so an agent can explore an authenticated area without driving a login every time.

Keep the MCP, narrowly. It remains better for short exploratory debugging where rich introspection beats token economy, and it needs no filesystem. Install both; make the CLI the documented default in the conventions, and reach for the MCP when a human is interactively poking at a stubborn page.

Naming note: the repository is currently playwright-mcp-template. If the CLI becomes the default path, that name will mislead people within a month. Worth renaming now while nothing depends on it.

What else gets a tool surface

The remaining rule is unchanged, and the reasoning still holds: every MCP server injects its full tool list into the agent's context, so five servers is plausibly 60+ tools, which measurably degrades tool selection. And an authoring agent that can read a secret eventually will, into a file or a transcript.

Section 07Test case → running script

  1. 01PullPractiTest case + steps → specs/*.md
  2. 02GateReject cases too vague to automate
  3. 03ExplorePlaywright MCP walks the live flow
  4. 04GenerateGenerator agent writes the spec
  5. 05Verifylint + tsc + run until green
  6. 06ReviewHuman PR review, always
  7. 07ReportRuns to PractiTest, defects to Jira

Two generation modes

Explore-first (default). The planner drives the running application through the Playwright MCP, captures accessibility snapshots, and generates against observed structure. Slower and it needs a working environment, but locators are real. This is the mode that justifies the MCP investment.

Spec-only (fallback). Generate from case text alone when no environment is available. Output is treated as a draft skeleton and marked test.fixme until it has been run against the app. Being explicit that this mode produces unverified code prevents a quiet flood of plausible-looking dead tests.

The quality gate is not optional

"Automatically create scripts just by looking at test cases" holds only for cases that are actually specific. A case reading "Verify the report is correct" cannot be automated by a human either. Step 02 scores each case on preconditions, concrete input data, an explicit expected result, and a defined starting state, and routes failures back to the case author with the specific gap named.

Expect this to reject a meaningful share of an existing legacy suite on first run. That is the system working — and it is worth saying out loud before anyone reads the rejection report as a tooling failure.

The healer, on a leash

Auto-healing is the most dangerous capability here: a healer that "fixes" a test to match newly-broken behaviour destroys the test's reason for existing. Constraints:

  • Healing runs in its own workflow and opens a pull request. It never pushes to a protected branch.
  • Locator and timing repairs only. A changed assertion or expected value is escalated to a human, never healed.
  • Every healed test is labelled with what changed, so review is a diff read rather than an act of faith.

Section 08Vault

Authentication

  • CI: JWT/OIDC via GitLab id_tokens — see section 13. This supersedes AppRole and removes the bootstrap-credential problem entirely.
  • Local: OIDC against the corporate IdP, falling back to AppRole or a short-lived dev token. Developers never hold a long-lived credential.
  • Tokens are renewed in-process for long shards and revoked in teardown.

Path layout

kv/data/qa/<env>/pools/<type>/<role>/<n>   # account pool — see section 10
kv/data/qa/<env>/app                      # base URLs, tenant ids
kv/data/qa/shared/integrations            # PractiTest, Jira, SMTP tokens
totp/keys/<env>-<account>                 # MFA seeds — never readable, code-only

KV v2 nests payloads under data.data; the adapter normalises this so callers never see the envelope. Secrets are fetched once per worker, cached in memory, and exposed only through the secrets fixture — never written to disk, never copied into process.env.

Leak control

This is the part that gets skipped and then bites. Playwright traces capture network payloads, screenshots and DOM; a login trace attached to a PractiTest run is a credential in a test management system. Mitigations: register secret values with a redaction helper at fetch time, scrub traces before attaching, keep storageState out of git and out of long-lived artifacts, and add a CI grep for known secret shapes over everything about to be uploaded.

Section 09MFA and OTP

One interface, two providers, and one race condition that will otherwise cost a week of intermittent failures.

interface OtpProvider {
  /** Watermark before the code is triggered. */
  arm(): Promise<Watermark>;
  /** Resolve a code produced after the watermark. */
  get(mark: Watermark): Promise<string>;
}

TOTP via Vault

Vault's TOTP secrets engine acts as the authenticator app: seeds are stored write-only and GET /v1/totp/code/<name> returns a current code. The seed never reaches the test process, which is a real security improvement over the usual pattern of pasting seeds into CI variables.

One sharp edge: if a code is fetched with two seconds left in its window, it expires between fetch and submit. The provider checks remaining validity and waits for the next window rather than returning a code about to die.

Email OTP via the mock inbox

The failure everyone hits: trigger the send, poll the inbox, read the newest message — and get the previous test's code. Hence arm(). Record the inbox high-water mark before triggering, then accept only messages newer than it. Combine with per-worker plus-addressing (qa+<runId>-<worker>@…) so parallel workers cannot read each other's mail, and consume the message once read.

Polling uses expect.poll with a bounded timeout so a missing email fails as a clear assertion rather than a hung test.

Adapting to an internal mail tool

The mock SMTP server here is an in-house tool, so the design cannot assume a known API. The adapter must be written against whatever it exposes, and the OTP flow needs four capabilities — the first three are hard requirements:

CapabilityNeeded forIf absent
Read messages programmatically
HTTP, IMAP, DB or filesystem		EverythingEmail OTP cannot be automated at all. Fall back to TOTP-only accounts for automation.
Filter by recipientParallel worker isolationSuite must run email-OTP tests serially, which will dominate runtime.
Stable ordering or timestampsThe arm() watermarkNo defence against reading a previous test's code. Intermittent, near-undebuggable failures.
Delete or mark-readInbox hygieneWorkable — fall back to timestamp watermarking, and add a purge step between runs.

If the internal tool exposes only SMTP with no read path, the pragmatic move is to run it alongside Mailpit in test environments purely as the readable sink, keeping the internal tool for whatever production-like behaviour it provides. That is a smaller change than it sounds — the application's SMTP host becomes an environment variable, and nothing in the framework changes.

Needed before phase 1: the internal tool's read interface — an API doc, a sample response, or just the name of the endpoint that lists messages.

Section 10Identity, sessions and account lifecycle

Three coupled mechanisms: never log in through the UI unless the test is about logging in, lease accounts from a pool rather than sharing them, and rotate passwords on a schedule without breaking either of the first two.

Storage state is the default; UI login is the exception

Driving a login form before every test is slow, and worse, it makes every test in the suite fail when login breaks — one defect, four hundred red results, and a triage report that tells you nothing. Authenticate once per role, reuse the session everywhere else.

Playwright's setup-project pattern is the right mechanism: a setup project authenticates each required role and writes a storage state file, and the test projects declare dependencies on it so they cannot start before it succeeds.

// playwright.config.ts — one setup project per role
projects: [
  { name: 'setup:auth', testMatch: /auth\.setup\.ts/ },
  {
    name: 'regression',
    dependencies: ['setup:auth'],
    use: { storageState: '.auth/${role}.json' },   // resolved per worker
  },
  {
    name: 'auth-flows',            // the exception
    testMatch: /login|mfa|password/,
    use: { storageState: undefined },              // must start signed out
  },
]

Making that exception explicit as its own project — rather than leaving it to each test to remember — means a spec cannot accidentally inherit a session it was supposed to establish itself. Enforce it with a lint rule: any spec tagged @auth must run in the auth-flows project.

Storage state is a credential

A storage state file contains live session tokens. Anyone who obtains it is signed in as that account, no password or MFA required. So it inherits every rule from section 08: written only to a gitignored .auth/ directory, never uploaded as a CI artifact, never attached to a PractiTest run, deleted in teardown, and regenerated per pipeline run rather than cached across days. Short-lived is the point — a stale session file is both a security exposure and a source of confusing mid-run failures when the server expires it.

Account pools, leased per worker

Accounts come from Vault organised by type and role, and tests declare what they need rather than naming a user:

kv/data/qa/<env>/pools/<accountType>/<role>/<n>
   → { username, passwordRef, mfaSeedRef, rotatedAt, state }

A worker-scoped fixture leases an account for the life of the worker and releases it at teardown. Worker-scoped rather than test-scoped matters: it means one login and one storage state per worker, not per test, while still guaranteeing two parallel workers never share an identity.

  • Leasing must be atomic. Two runners starting simultaneously will otherwise both take account 1. A Vault CAS write, or a small lease record with a TTL, prevents it. Without this, parallel runs corrupt each other in ways that look exactly like flaky tests.
  • Pool exhaustion needs a real error. "No available account for role approver: pool size 4, all leased" — not a timeout ten minutes later.
  • Leases must expire. A crashed runner that never releases its lease will otherwise shrink the pool permanently.
  • Size pools against worker count. Pool size must be at least the maximum concurrent workers per role, or the suite serialises on account availability and nobody understands why it got slow.
  • Mutating tests need their own accounts. A test that changes a user's profile or permissions should lease from a pool marked disposable, not from the shared read-only pool.

Scheduled password rotation

Rotation is a scheduled GitLab pipeline, not something the test run does. Interval is configuration, per environment and per account type:

rotation:
  enabled: true
  maxAgeDays: 60            # per account type, overridable per role
  jitterDays: 5             # avoid rotating the whole pool at once
  blackout: { start: '18:00', end: '06:00' }   # never during the nightly run
  onFailure: quarantine     # remove from pool, alert, do not retry blindly

The order of operations is what makes this safe. Change the password in the application first, verify a login succeeds with the new one, and only then write it to Vault. Writing to Vault first and failing the application change leaves an account nobody can use and a credential store that lies about it.

  1. Acquire an exclusive lease on the account, so no run can pick it up mid-rotation.
  2. Change the password in the application through its own API or UI flow.
  3. Verify by authenticating with the new password.
  4. Write the new value to Vault as a new KV v2 version — the version history is your rollback.
  5. Invalidate any cached storage state for that account.
  6. Release the lease.
  7. On failure at any step: mark the account quarantined, remove it from the pool, and alert. Never leave it in a state where the next run finds it broken.

The blackout window matters more than it looks. Rotating an account while the nightly suite is mid-flight produces authentication failures that look like application defects and will consume a morning of triage. Jitter matters for the same reason at pool scale — rotating every account on day 60 means one night where everything is briefly invalid.

Two smaller points that prevent recurring pain: many enterprise applications enforce password history and minimum-age rules, so the generator must produce values that satisfy the real policy and rotation cannot run more often than the minimum age allows. And if the application forces a change-password screen on first login after a reset, that interstitial has to be handled in the rotation flow, or every subsequent storage state capture silently lands on the wrong page.

Section 11PractiTest results

Identity mapping

Specs carry { type: 'practitest', description: '4821' } annotations. The reporter resolves display IDs to instance IDs via set-ids plus name_exact, caching the map so resolution is not repeated every run. A spec whose case cannot be resolved is reported loudly but does not fail the suite.

Working inside the API envelope

ConstraintHandling
≤ 20 instances / POSTReporter buffers all results to onEnd, then chunks into 20s.
≤ 30 calls / minuteToken-bucket limiter shared across the process; exponential backoff with jitter on 429.
Sharded CIShards write result JSON as artifacts; a single post-job merges and posts once. Avoids N shards × M calls blowing the limit.
AttachmentsBase64, failures only, size-capped, scrubbed. Traces are large — cap before encoding.

Authentication uses the PTToken header with a Personal API Token so actions are attributed to a real user and inherit that user's permissions. Step-level results are posted where the case has structured steps and the spec maps to them; otherwise a single run status with the failure message as the actual result.

Section 12Jira Data Center

Data Center is not Cloud with a different URL. Four differences bite an integration written against Cloud documentation.

Cloud (not applicable)Data Center (target)
Endpoint/rest/api/3//rest/api/2/
AuthBasic: email:tokenAuthorization: Bearer <PAT>
Rich textAtlassian Document Format (JSON)Wiki markup (string)
Official MCPYesNo — cannot connect

The auth difference is the one that wastes an afternoon: a Data Center PAT sent as Basic auth returns 401, not a helpful error. PATs require Jira DC 8.14 or later — worth confirming your instance version early, because below that the only options are password basic auth or OAuth 1.0a, both considerably worse.

Confirmed configuration

JIRA_BASE_URL = https://jira.<org>.<internal-domain>/rest/api/2
JIRA_AUTH     = Authorization: Bearer ${PAT}   # from Vault, never CI plaintext
JIRA_TLS      = NODE_EXTRA_CA_CERTS=<internal root CA>  # see section 13

PAT lifecycle

Jira DC PATs take an optional expiry, and administrators can enforce a maximum lifetime or forbid non-expiring tokens via system properties. Two consequences worth designing for now rather than discovering at 2am:

  • A token that silently expires turns every nightly run's reporting step into a 401. The Jira client should treat 401 as a distinct, loudly-reported condition — "credential expired or revoked" — not fold it into generic request failure.
  • Store the PAT in Vault, not in CI variables. Rotation then means updating one Vault path rather than hunting through pipeline configuration, and the audit trail comes free.
  • Use a dedicated service account, not a person's PAT. Personal tokens inherit that person's permissions and die when they change role or leave.

Integration behaviour

  • Inbound: a spec's jira annotation links it to the story or defect it covers, giving traceability in both directions.
  • Outbound: on failure, create or update a defect. Deduplicate on a fingerprint of test ID plus normalised error, so a flaky test produces one ticket with a failure count, not forty tickets.
  • Reopen, don't duplicate: if a matching closed defect exists, reopen with a comment linking the new run. Note that DC transitions are workflow-specific — the adapter must look up available transitions by name rather than hard-coding IDs, which differ per project.
  • Guard rail: defect creation is off by default and enabled per-pipeline. An automated defect filer pointed at a broken environment can create hundreds of tickets in one night.
  • Formatting: descriptions are built as wiki markup. Reusing a Cloud ADF payload here produces tickets displaying raw JSON.

The conversational access that was lost

Losing the official MCP means agents can no longer be asked "what's the acceptance criteria on FIN-2210?" during generation. Two ways to recover part of it:

  • A read-only Jira CLI (jira:issue <key>) that prints an issue as markdown. Cheap, fully under your control, and enough for the generation workflow's actual need — pulling acceptance criteria into context.
  • A community MCP server. sooperset/mcp-atlassian supports Jira Server/DC 8.14+ with PAT auth and is actively maintained. Revised recommendation given the environment: assume this will not clear security review. Handing a third-party package a PAT against an internal, self-hosted Jira is a supply-chain question your security team will reasonably say no to, and it is not worth spending review capital on a convenience feature.

Recommendation: build the CLI, and only the CLI. The reporter needs the REST client anyway, so the CLI is a thin wrapper over code you are writing regardless — no new dependency, no new egress path, no review.

Section 13GitLab CI

GitLab changes three decisions from earlier drafts, all in the plan's favour — it removes the AppRole bootstrap problem, it answers the report-hosting question, and it puts results on the merge request.

Vault authentication via OIDC, not AppRole

This supersedes the AppRole recommendation in section 08 for CI. GitLab issues a signed JWT per job through the id_tokens keyword, Vault validates it against your GitLab's OIDC discovery URL, and the secrets keyword uses it automatically. There is no secret_id to deliver, wrap, or rotate — the bootstrap credential problem disappears.

.vault-auth:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.<internal>
  secrets:
    PRACTITEST_TOKEN:
      vault: qa/shared/integrations/practitest@kv
    JIRA_PAT:
      vault: qa/shared/integrations/jira@kv

The real advantage is bound claims. A Vault role can require project_path and ref to match, so a job on a feature branch of a forked project cannot read staging credentials even with a valid token. That is meaningfully stronger than AppRole, where possession of the secret ID is the whole authorisation. Keep AppRole only for local developer runs outside GitLab.

Your Vault is a separate system — what that changes

It does not break this design; a separately-operated Vault is the normal topology for JWT auth. But it makes two prerequisites explicit, and both belong to a different team than the one building this framework.

  • Someone must enable and configure the JWT auth backend on Vault, create the role, and set the bound claims. This is a Vault administrator task with its own request process. Nothing in the pipeline works until it is done, so raise it in phase 0.
  • Vault must be able to validate GitLab's token signature, and there are two ways to arrange that. oidc_discovery_url has Vault fetch GitLab's keys at authentication time — clean, self-maintaining, but it requires Vault to reach GitLab over the network, which across security zones is not a given.

If that path is blocked, the fallback is jwt_validation_pubkeys: GitLab's signing public keys are configured directly into the Vault backend, and no network call is made. The three options — oidc_discovery_url, jwks_url and jwt_validation_pubkeys — are mutually exclusive, so this is a deliberate choice, not a layered fallback.

The trade-off is real and worth stating to whoever configures it: static public keys remove the network dependency but also remove automatic key rotation. When GitLab rotates its signing key, every pipeline fails authentication until someone updates Vault by hand. Prefer discovery if the network path can be opened; choose static keys knowingly, with a documented owner, if it cannot.

Confirm the direction of reachability too. OIDC discovery needs Vault → GitLab, while the runner needs GitLab runner → Vault. These are separate firewall rules and it is common for one to exist without the other.

  • artifacts:reports:junit puts pass/fail directly in the merge request widget. This is the fastest feedback surface you have and it costs one line — emit JUnit alongside the other reporters.
  • GitLab Pages hosts the rich HTML report at a stable per-run URL, which resolves the open hosting question from section 16. Caveat for self-managed: Pages must be enabled on your instance, and on an internal GitLab it may be restricted or unavailable. Runner and environment notes

  • Use Playwright's official container image matching the pinned version exactly. Version drift between image and dependency is a top source of "works locally, fails in CI".
  • Proxy, CA bundle and registry variables from section 14 belong in the job environment, not baked into the image.
  • Vault dev mode and the mail mock run as services for MR pipelines; nightly uses the real instances.
  • Confirm whether runners are shared or project-specific. On shared runners, secrets fetched into the job environment are exposed to whatever else that runner executes — in a regulated environment, project-specific runners are the expected answer.
  • Local Docker here is 20.10.11, old enough to be worth upgrading before relying on service containers. The vault CLI is absent, so the adapter should speak HTTP directly — the better dependency choice regardless.

Section 14Operating inside a restricted network

A self-hosted Jira on an internal domain implies a proxied, privately-signed, mirror-fed environment. None of the tooling below works out of the box in one, and every failure mode presents as something other than what it is.

The four that will bite in the first week

ProblemPresents asFix

TLS interception		 SELF_SIGNED_CERT_IN_CHAIN on any call to Jira, PractiTest or Vault NODE_EXTRA_CA_CERTS=/path/root.pem

The CA one deserves emphasis because it is genuinely misleading: never reach for NODE_TLS_REJECT_UNAUTHORIZED=0 to make it go away. It disables certificate validation process-wide, including for the Vault calls carrying your credentials, and it has a way of surviving into production pipelines. Point Node at the real CA bundle instead.

Playwright's browser binaries are the other classic stall. Playwright honours HTTPS_PROXY, and PLAYWRIGHT_DOWNLOAD_HOST redirects the installer at an internal artifact server — worth mirroring the binaries there, since browser downloads are large, frequent in CI, and the first thing a proxy throttles. Per-browser overrides exist (PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST) if only some are mirrored.

Data governance for the generation loop

This is the constraint most likely to be raised late by someone who was not in the room, so it belongs in the plan now. Both supported AI clients send context to a cloud model. During explore-first generation that context includes accessibility snapshots of real application screens, and during case-pulling it includes Jira and PractiTest content.

  • Generation runs against test environments only, never production and never an environment seeded from a production copy. This should be enforced by configuration — the MCP browser target is an allowlist of non-production hosts — not by convention.
  • Synthetic test data only in any environment the agents explore. A masked-but-real dataset is still a dataset leaving the building inside a snapshot.
  • Get the AI tooling's data-handling terms reviewed before phase 2, not after. Approval for Copilot and Claude Code may already exist organisation-wide; if it does not, phase 2 is blocked regardless of how good the framework is.
  • The framework itself sends nothing anywhere — this constraint applies to the authoring loop, not to test execution. Worth stating clearly, because the two get conflated in review.

Vault, in an environment that probably already has one

An organisation of this shape likely runs Vault Enterprise already, which changes three assumptions in section 08: namespaces prefix every API path, the auth methods you need may not be enabled on your namespace, and mount paths are set by a platform team rather than chosen by you. Confirm namespace, mount points, and whether the TOTP secrets engine is enabled at all — it is comparatively rarely used and may require a request.

Section 15The run report

Serenity's real achievement is not that it is pretty. It is that a product owner can read it without knowing what a locator is. That is the property worth copying — and it is orthogonal to visual polish.

One data model, three renderings

The mistake to avoid is generating HTML directly from the reporter. Everything downstream — the report, the email, the PractiTest push, the triage agent — needs the same facts, and each one re-deriving them from Playwright's raw output guarantees they eventually disagree. So the reporter's only job is to emit a normalised, versioned run-result.json; every consumer reads that.

  1. Sourcerun-result.jsonCanonical, versioned, shard-merged
  2. Render ARich HTMLSelf-contained, browser, full evidence
  3. Render BEmail digestOutlook-safe, ~600px, links out
  4. Render CPractiTest + JiraRuns, defects, attachments

A useful side effect: the report becomes testable. Feed a fixture run-result.json with a known mix of pass, fail, flaky and skipped, and assert the rendered HTML. Reports that are generated only from live runs are never tested and quietly rot.

What "comprehensive" should actually contain

Ordered by how often someone genuinely needs it — not by what is easy to compute.

BandContentAnswers
Verdict Pass / fail / flaky / skipped counts, overall status, run duration, environment, build and branch, trigger, timestamp with timezone Do I need to care, right now?
Triage summary Failures grouped by agent-assigned cause, counts per category, confidence, "new since last run" vs known issues Is this our bug or the environment's?
Trend Pass rate and flake rate over the last N runs, duration trend, newly-failing and newly-fixed lists Is quality moving, and which way?
Coverage PractiTest set coverage — cases automated vs total in scope, cases not executed, specs with no case ID What did we not test?
Per test PractiTest ID (linked), title, suite, owner, duration, retries, first-run outcome, browser/shard, tags Which case, and how long?
Evidence Narrative steps in business language, screenshots at each step, error with the failing assertion highlighted, network log excerpt, console errors, trace link, video What actually happened?
Health Slowest tests, flakiest tests ranked by rate not count, quarantined list with age, shard balance, retry budget consumed What is rotting?

Two of these are the ones teams skip and later wish they had. Flake rate as a rate, not a count — a test that fails 1 in 3 runs matters far more than one that failed twice ever. And first-run outcome recorded separately from final outcome, because a suite that is green only after retries is not green, and the distinction disappears if you record only the final state.

Getting flaky right in the reporter

A detail that produces wrong numbers if missed: onTestEnd fires once per attempt, including every retry, so counting statuses there double-counts retried tests. Flakiness is only knowable once all attempts are done. Aggregate in onEnd using test.outcome(), which returns expected, unexpected, flaky or skipped — that is the API that actually encodes "passed, but not first time".

The Serenity qualities worth carrying over

  • Narrative steps in business language. Playwright's test.step() titles become the report's narrative, so step naming stops being cosmetic and becomes the report's readability. This should be a lint-enforced convention: steps are named for intent, not mechanics — "Submit the expense claim", never "click #submit-btn".
  • Evidence attached to the step, not the test. A screenshot at the failing step is worth ten at the end. Capture per step on failure paths.
  • Requirements coverage as a first-class view. With PractiTest IDs on every spec, the report can show set coverage directly — the closest thing to Serenity's living documentation available here, and more valuable than any visual flourish.
  • Readable without the code. The test is the disclosure, not the source file. Every failure states what was expected in plain language before it shows a stack trace.

Build it, or theme Allure?

Worth deciding deliberately rather than by default. Allure is the most capable off-the-shelf option — history, trends, categories, step detail, attachments — and adopting it costs days rather than weeks. What it does not give you is a PractiTest coverage view, the triage verdict column, or your own visual identity, and its categories mechanism is regex-over-error-text rather than genuine analysis.

Recommendation: emit run-result.json plus Allure results from the same reporter. Use Allure immediately for deep per-test forensics, and build the bespoke report as the executive and stakeholder view fed by the same JSON. They serve different readers, the duplication is small, and it avoids a month of rebuilding trend charts that already exist.

The report's visual spec

Self-contained single HTML file — inlined CSS and JS, evidence embedded or referenced by relative path, no CDN. It must open from a file share with no server. Structure: a status band that reads correct at a glance from across a desk, a triage summary, filter chips (status, suite, category, owner, "new only"), a virtualised results table for suites in the thousands, and an expandable evidence drawer per test rather than a separate page. Semantic colour for pass/fail/flaky/quarantined is a data encoding here, kept distinct from the brand accent, and never the only signal — pair it with shape or label for accessibility.

Section 16Delivery by email

The instinct is to email the pretty report. That does not work, and knowing why up front saves building something twice.

The constraint

Outlook desktop renders HTML through the Word engine: no flexbox, no grid, no CSS custom properties, no media queries, no reliable border-radius, no background images. Microsoft has said it will retire Word-based rendering in favour of the Chromium engine, but an enterprise on managed desktops will be behind that curve for a long time. Two further traps:

  • Base64 data: images do not work. Gmail strips them; Outlook blocks them outright. Inline images must be CID attachments — which Nodemailer supports natively — or hosted on an internal server and linked.
  • An .html attachment will probably be quarantined. HTML attachments are a standard phishing vector and corporate mail filters routinely strip them. Do not make the rich report an attachment.

The design that survives this

  1. Publish the rich report to the CI artifact store or an internal web server, at a stable per-run URL.
  2. Email a digest, not the report. Table-based layout, ~600px, fully inlined CSS, no JavaScript, a plain-text alternative part for accessibility and filters. It carries the verdict band, the counts, the triage summary, and the top failures — enough that someone can decide whether to open anything at all.
  3. Link out for everything else. One prominent "Open full report" bulletproof button (VML-wrapped so Outlook renders it), plus deep links per failing test.
  4. Degrade to inline detail only if hosting is unavailable. If nothing can host the report, expand the digest to include the top failures' errors as text. Never attach the HTML.

Nodemailer specifics

  • SMTP credentials come from Vault via the same secrets fixture, never from CI variables.
  • Set both html and text. Some corporate gateways score HTML-only mail as spam.
  • Inline images as attachments with a cid: reference. Keep them few and small — a status band and a trend sparkline, not screenshots.
  • Send once, from the merge job, after all shards report. Per-shard emails are how a team learns to filter your notifications into a folder they never open.
  • Subject line carries the verdict, not the tool: [FAIL] Regression · staging · 12 failed, 4 flaky · build 4821. It should be triageable from a phone lock screen.
  • Failure to send must not fail the build — log, retain the digest as an artifact, and move on.

Section 17The failure triage agent

The most valuable component in this plan, and the one most likely to be built wrong — because the obvious implementation is to hand every failure to a model and ask what happened.

Two passes before any AI runs

Pass 1 — cluster. Group failures by signature: normalised error, failing step, and time window. If forty tests fail with the same connection error in the same two minutes, that is one environment incident, not forty defects. Triage the cluster once.

This single decision does three things at once: it stops forty Jira tickets being filed on a bad night, it cuts triage cost by roughly the clustering factor, and it makes the answer more accurate — because breadth is itself the evidence for an infrastructure cause, and a per-test view cannot see it.

Pass 2 — classify by rule. A large share of failures are deterministically identifiable and need no model at all:

SignalConclusion
Passed on retryFlaky — by definition, not inference
Network log contains 5xx from the appApp or infrastructure, never locator
Vault or mail adapter threwDependency
DNS / ECONNREFUSED / TLS errorNetwork or environment
Error fingerprint matches an open Jira defectKnown issue — link, do not re-file
Every test in the run failed at loginEnvironment or credentials

The model is then asked only about what the rules could not settle — which is where judgement genuinely is required, and which is a small fraction of a typical run.

The taxonomy

CategoryDistinguishing evidenceRoutes to
Application defectElement present and correct, app returned a wrong value or state; error visible in UI; server 5xx on a valid requestJira defect, dev team
Locator / UI driftTarget absent from DOM snapshot but a near-match exists with a changed name, role or structureHealer PR, QA
Test dataPrecondition record missing, already consumed, or in an unexpected state; unique-constraint collisionsQA, data setup
Network / infrastructureConnection failures, gateway errors, DNS, TLS; correlated across unrelated testsPlatform, no ticket per test

What the agent is given, and what it must return

Evidence: the normalised error and stack, the failing test.step() and the steps that preceded it, the DOM snapshot at failure, the network log with status codes, console errors, before/after screenshots, retry history, this test's failure history, what else failed in the same window, and the commits deployed since the last green run.

Output is a strict JSON contract, validated on receipt — free-text findings cannot be aggregated, filtered, or trended:

{
  "clusterId": "c7f2",
  "category": "application-defect",
  "confidence": "high",              // high | medium | low — never a fake percentage
  "summary": "Approval limit not enforced for amounts over 10,000",
  "evidence": [
    "POST /api/claims returned 201 for amount=15000",
    "No validation error rendered; assertion expected 'exceeds limit'",
    "Same behaviour on both retries — not timing-related"
  ],
  "affectedTests": ["TC-4821", "TC-4822"],
  "recommendedAction": "file-defect",  // file-defect | heal | fix-test | fix-data | escalate | none
  "suggestedOwner": "payments-team",
  "needsHumanReview": false
}

Guardrails

  • Advisory by default. The agent annotates the report. Filing a Jira defect stays behind the same per-pipeline switch as section 11, and auto-filing should stay off until the category accuracy has been measured over several weeks.
  • Every claim cites evidence. A verdict without a specific artifact reference is rejected by the schema validator. This is what makes the output reviewable rather than merely confident-sounding.
  • Three confidence levels, not percentages. A model's "92% confident" is not a calibrated probability, and printing it as one manufactures trust the number cannot support.
  • Low confidence is a valid answer. needsHumanReview routes it to a person unclassified. An agent that always produces a category will produce wrong categories.
  • Triage never heals. It may recommend heal; the healer's own constraints from section 07 still apply, and a human still reviews the PR.
  • Traces carry application data. Sending them to a model is the same governance question as section 13 — scrub before sending, and only from non-production environments.

Measuring whether it works

A triage agent nobody trusts is worse than none, because it adds a step without removing one. So instrument it: record the agent's category alongside the human's eventual verdict, and report agreement rate per category monthly. Expect it to be genuinely good at network, environment and dependency — where evidence is unambiguous — and weakest at distinguishing application defect from test logic defect, which needs requirement context it may not have. Publishing that breakdown is what earns the team's trust in the categories that are reliable.

Section 19Self-critique

Written adversarially against the plan above. Severity reflects how much of the design has to change if the concern proves out.

The headline promise is oversold

High

"Automatically create scripts just by looking at test cases" implies a hands-off pipeline. Realistically, explore-first generation against a well-written case produces a spec needing minor review most of the time; against a typical legacy case it produces something needing real work. The quality gate in section 07 mitigates but does not remove this.

ResponsePhase 2 measures the hit rate on real cases before anyone commits to a target. Frame the deliverable as "drafts a reviewable spec" rather than "writes the test", and let the measured number set expectations.

Six integrations at once is the classic way this dies

High

Playwright, MCP, Vault, mock SMTP, Jira, PractiTest, plus a novel framework shape and an agent workflow. Any one of them can absorb a week. Built in parallel, nothing is demonstrable for two months and the first integration problem stalls everything.

ResponseThe phasing is explicitly a walking skeleton, and every phase has a demonstrable exit criterion. If the plan is adopted, the phase boundaries should be treated as hard.

The four-layer split is a bet, not a proven pattern

Medium

The argument that a closed vocabulary beats POM for generation is reasoned, not measured. Models have seen enormous quantities of POM in training and comparatively little of this shape, so priors may partly work against it. It is also more structure than a small suite needs.

ResponseFalsifiable in phase 2 — generate the same ten cases against both shapes and compare. The layers are conventions plus lint rules, so reverting toward POM is cheap if the data says so.

Traces and attachments are a live credential leak path

High

Doing Vault properly and then base64-ing an unscrubbed trace of a login flow into PractiTest defeats the entire exercise. Scrubbing is easy to specify and easy to implement incompletely — a password typed character by character does not appear as a contiguous string in a DOM snapshot.

ResponseTreat this as a feature with its own test: a deliberate leak test that fails if a known canary value survives into any artifact. Until that test exists, attachments stay off.

The healer can quietly erase regression coverage

Medium

A locator repair and a bug are indistinguishable from inside the test. If the login button's accessible name changes because someone broke the i18n bundle, healing the locator hides a real defect and the suite goes green on a broken build.

ResponsePR-only healing, no assertion changes, labelled diffs. Worth adding: a healer that files a Jira ticket instead of only a PR when it repairs the same locator more than once in a fortnight.

"Vault gets no MCP" will feel obstructive

Medium

The first time someone debugs a credential problem, wanting the agent to just read the secret is entirely natural, and the rule will get quietly broken. Security controls that depend on discipline decay.

ResponseMake the safe path easier than the unsafe one — a vault:check CLI that reports whether a path resolves and what shape it has, without ever printing values. Most debugging needs the existence check, not the secret.

PractiTest rate limits are tighter than they look

Medium

Thirty calls per minute is not much once instance resolution, run creation and attachment uploads are counted, and sharded CI multiplies callers. Naive implementation hits 429s on the first full nightly run.

ResponseThe merge-then-post design in section 10 addresses it, at the cost of no live progress during a run. That trade should be stated to stakeholders who may expect results appearing in real time.

Supporting both AI clients equally doubles the surface that can rot

Medium

Both Copilot Chat and Claude Code are now first-class, which is a real requirement rather than a preference — but generating copilot-instructions.md and CLAUDE.md from one source only keeps the text aligned. Different context windows, tool-calling behaviour and MCP support still produce different code from identical instructions. Two init-agents loops (--loop=vscode and --loop=claude) also means two agent definition sets to keep current.

ResponseAccept the cost, contain it three ways. Lint, types and the test run are the equaliser — whatever writes the code passes identical gates. Run the phase 2 hit-rate experiment separately per client so divergence is measured, not assumed. And add a CI check that both agent definition sets were regenerated against the installed Playwright version, since a stale set fails silently.

Jira Data Center weakens the traceability story

Medium

New in this draft. With no official MCP, agents cannot pull acceptance criteria conversationally while generating, so the requirement context that would improve generated assertions has to be fetched explicitly or pasted by a human. Self-hosted Jira also tends to mean network restrictions — CI may not reach it at all without a firewall exception, which nobody has requested yet.

ResponseThe read-only CLI in section 11 covers the generation-time need at low cost. The network path is a genuine unknown: confirm CI-to-Jira reachability during phase 0, not phase 4, because an infrastructure request has a lead time no amount of code can shorten.

Dual source of truth between Jira and PractiTest

Medium

Requirements in Jira, cases in PractiTest, code in git — three systems that will drift. A case updated in PractiTest does not notify the spec; the spec silently tests yesterday's requirement.

ResponseStore a content hash of the source case in the spec annotation and add a CI check that flags specs whose upstream case changed. Cheap, and it converts silent drift into a visible task.

Password rotation is the most dangerous automation in this plan

High

Everything else fails safe. Rotation writes to a live system, and its failure modes lock accounts out: a password changed in the app but not persisted to Vault, a rotation firing mid-run, an application-enforced history rule silently rejecting the new value, or a forced change-password interstitial that the flow does not expect. In a regulated environment, repeated failed logins against a locked account may also trip security monitoring — which is a conversation nobody wants to have unprepared.

ResponsePhase 1b exists precisely so this is not rushed alongside the pool work. App-first-then-Vault ordering, verify before persist, exclusive lease during rotation, blackout windows, jitter, and quarantine rather than retry. Test it against a disposable pool before it ever touches the shared one, and tell whoever owns account security that this automation exists before it runs.

Cross-team dependencies now sit on the critical path

High

New with the confirmation that Vault is operated separately. Phase 1 cannot complete until a Vault administrator enables the JWT backend and creates a role with bound claims, and OIDC discovery additionally needs a network path from Vault to GitLab that may not exist. None of this is work the QA team can do, estimate, or expedite, and it is the classic cause of a plan that looks on track until it stops entirely.

ResponseRaise both requests in phase 0, before writing the Vault adapter. Build the adapter against a local Vault dev container so progress does not depend on the request landing, and keep the auth method behind an interface so switching from AppRole to OIDC — or to static public keys — is a configuration change rather than a rewrite.

Both Playwright agent tools are pre-1.0

Medium

@playwright/mcp is at 0.0.79 and @playwright/cli at 0.1.18. The agent definitions are explicitly meant to be regenerated whenever Playwright updates, which means the command surface and generated files this plan describes will move. Building tooling tightly around either is building on a moving foundation.

ResponsePin exact versions and treat upgrades as deliberate, tested changes rather than routine dependency bumps. Keep project-specific logic — case pulling, result pushing, conventions — in your own scripts rather than inside generated agent definitions, so an upgrade regenerates their files and not yours. The CI check for agent-definition freshness exists for exactly this.

The account pool is a shared mutable resource, and those always leak

Medium

Leases assume every holder releases them. Crashed runners, cancelled pipelines and killed jobs do not. Over weeks a pool silently shrinks until the suite serialises or fails on exhaustion, and the symptom — intermittent slowness, then sudden failures — looks nothing like the cause. Tests that mutate their leased account's state compound it.

ResponseTTL every lease so abandonment self-heals, report pool utilisation in the run report so shrinkage is visible before it is critical, and separate disposable pools for mutating tests from read-only shared ones. Treat "pool exhausted" as a first-class error with a named role and count, never a timeout.

A bespoke report is a product, and products need owners

Medium

"Prettier than the Playwright report" sounds like styling; a Serenity-class report is virtualised tables, trend storage, evidence handling and a build pipeline. It will take longer than estimated, and in eighteen months it is either someone's job or it is abandoned at whatever state it reached — and abandoned reporting is worse than the stock report, because people stop trusting it before they stop receiving it.

ResponseThe Allure-in-parallel recommendation is the hedge: if the bespoke report stalls, the team still has capable forensics and nothing is blocked. Keep the bespoke surface deliberately small — executive view, coverage, triage — and resist rebuilding what Allure already does well.

Trend data needs somewhere to live, and nothing owns that yet

Medium

Flake rate, pass-rate trends and "new since last run" all require history, but the plan describes per-run artifacts only. CI artifact retention is typically days to weeks, and it is not a queryable store. Without deciding this, the most valuable band of the report silently degrades to a single run's snapshot.

ResponseDecide it in phase 5, before building the trend views. Cheapest workable option: append each run's summary to a small committed JSON-lines file or an internal object store bucket, keyed by branch and environment. A database is not needed for hundreds of runs a year, and choosing one is how this stalls.

The triage agent's confidence will be over-trusted

High

The genuine risk is not that it is wrong — it will be, sometimes — but that a wrong verdict is stated fluently next to correct ones and is indistinguishable from them. "Test data issue" on what is actually a production-affecting defect is a miss that a plausible explanation actively conceals, and the report's authority makes it worse.

ResponseThree levels rather than percentages, mandatory evidence citations, a valid "needs human review" outcome, no auto-filing, and a published per-category agreement rate. The report should also visually mark AI verdicts as distinct from rule-derived ones, so readers know which is which. Treat any category below a measured agreement threshold as advisory-only in the UI.

Email is a notification channel people learn to ignore

Low

A nightly mail that is green 90% of the time trains its recipients to filter it. The value is in the exceptions, and undifferentiated daily mail destroys the signal — while a corporate mail gateway may also throttle or quarantine a repeating automated sender.

ResponseMake the subject line carry the verdict so it is triageable unopened, and consider sending detail only on failure or change of state, with a weekly summary otherwise. Confirm the sending account is a sanctioned service mailbox rather than a person's.

Generation cost has not been estimated

Low

Explore-first generation is token-expensive: snapshots are large and the verify-repair loop iterates. Across hundreds of cases, plus healer runs, this is a real budget line nobody has priced.

ResponseMeasure cost per generated test during phase 2 alongside the hit rate. It is one extra number from an experiment already planned.

The internal mail tool is the largest remaining unknown

High

Severity raised from the previous draft. An in-house SMTP mock has no documentation I can design against, and the email-OTP flow depends on three specific capabilities it may not have. If it lacks a read API, a whole authentication path is unautomatable until something changes.

ResponseThe capability table in section 09 states exactly what is required and what each gap costs, and the Mailpit-as-sink fallback keeps the plan viable in the worst case. But this is now the top item to resolve before phase 1 starts.

Environment friction is underweighted

Medium

Raised from Low. Windows host, Docker 20.10.11, no Vault CLI — and now a self-hosted internal network on top, meaning proxy, private CA and registry mirror configuration before a single test runs. Line endings, path separators and container networking each cost an afternoon, and none of it appears in the phase estimates.

ResponseSection 13 now enumerates the specific failure modes. HTTP-API-only Vault access avoids the CLI dependency. Enforce LF via .gitattributes from the first commit, and confirm whether CI is Windows or Linux — if they differ, that difference will surface as flakes.

Approval to send context to a cloud model may not exist

High

New, and potentially fatal to the central premise. The entire generation approach depends on an AI client receiving application snapshots and test case content. In a self-hosted, regulated environment that is a data-governance question with a real chance of a restrictive answer — and it is the kind of question that surfaces at phase 3 review, after the framework is built around an assumption nobody validated.

ResponseMove it to phase 0 as a written confirmation, not a corridor conversation. If the answer is restrictive, the framework itself still delivers value — the four-layer shape, Vault, OTP, PractiTest and Jira integration all stand without any AI in the loop. Only the generation loop is lost, and knowing that in week one is worth far more than discovering it in month three.
