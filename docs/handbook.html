Section 01Start here

Four commands to a green suite. None of it needs an application: the framework proves itself against in-process fakes, so nothing internal has to be reachable before you see it work.

npm install
npx playwright install chromium

npm run verify          # lint + types + generated-file checks + 250 framework tests
npx playwright test     # the framework's own suite; no application attached yet

If both are green you have a working framework, its guardrails, and every integration adapter exercised against in-process fakes. No credential, no network beyond the npm registry, and no Docker.

There is no application attached yet. main ships the framework plus one template pack, src/targets/example-app/, which has a deliberately unusable host and no specs — copy it, rename it, and replace its contents. Section 09 is the four-step path; a worked implementation against a live public site lives on the saucedemo/extensive-coverage branch, and what it taught the framework is written up in docs/learnings.md.

What each command actually does

CommandWhat it proves
npm run verifyThe conventions execute, the types hold, the generated agent files are current, and the framework's own 227 tests pass. This is what CI runs on every merge request.
npx playwright testAdds the browser projects: a session is established once, specs run against it, and the drift harness proves locator drift can be induced on demand.
npm run report:renderTurns the run into a self-contained HTML report you can open from a file share.
npm run vault:checkConfirms every credential path the target needs resolves — without ever printing a value.

The one idea to hold onto

Orientation

A generated test is a constrained search. Everything here exists to shrink the search space and to tell a model — without a human — that it went wrong. That is why the vocabulary is closed, why conventions are lint rules rather than prose, and why locators come from a snapshot of a real page rather than from a model's priors. If a change makes generation freer, it is probably the wrong change.

Section 02How it works, end to end

A written test case becomes a running spec, a run becomes one canonical fact set, and failures are grouped and classified before a human reads them. Each hop is a separate tool, so the chain can be stopped anywhere.

  1. 01Casecases/*.yaml from Jira or PractiTest
  2. 02GateReject cases too vague to automate
  3. 03Exploreplaywright-cli snapshots the live page
  4. 04GenerateAgent writes a spec from the catalog
  5. 05Verifylint + tsc + run, until green
  6. 06ReviewHuman reads a diff
  7. 07ReportOne JSON → report, email, PractiTest
  8. 08TriageCluster → rules → model

The feedback loop that makes generation work

Steps 04 and 05 are a loop, and the loop is the product. An agent writes a spec; npm run lint and tsc --noEmit answer in structured, quotable errors; the agent repairs. Nothing in that cycle needs a human, which is the whole reason the conventions are executable rather than documented.

write  →  lint + tsc + playwright test  →  structured errors  →  repair

Anything a person has to catch by eye is a convention that has not been finished. When you add a rule to docs/CONVENTIONS.md, ask immediately whether it can be a lint rule instead — and if it can, write the rule.

Where the data goes after a run

Exactly one artifact carries facts: run-result.json, written by the reporter in src/support/reporters/. The HTML report, the email digest, the PractiTest push and the triage pipeline all read it and never re-derive anything from Playwright's raw output. That is what stops four renderings of the same run quietly disagreeing about how many tests failed.

Source run-result.jsonNormalised, versioned, shard-merged. Flaky is computed in onEnd from test.outcome(), never counted per attempt.
Render A report-out/index.htmlSelf-contained: inlined CSS and JS, no CDN, opens from a file share.
Render B Email digestTable layout, 600px, inlined styles, plain-text alternative. Links the report, never attaches it.
Render C PractiTest & JiraBatched, throttled, scrubbed. Best-effort — never turns a green suite red.

Section 03End-to-end flow

One picture of the whole thing: where a test comes from, what turns it into code, what runs it, and what happens to the result. Every arrow is a file or a command that exists in this repository.

Reading it

  • The accented path is the spine. A case becomes a spec, a spec becomes a run, a run becomes run-result.json. Each stage hands the next a file rather than a convention, which is what makes the joins testable.
  • The dashed edges are feedback, not flow. The gate returns structured errors to the agent; the session written by setup:auth is read back by every other project.
  • Nothing crosses a stage boundary informally. Generation cannot read a Jira ticket, only the yaml. Reporting cannot read Playwright's raw output, only run-result.json. That is what stops four renderings of the same run disagreeing about how many tests failed.
  • The dashed boxes are other people’s systems — the application under test, and HashiCorp Vault, which issues the account each worker signs in with, the TOTP code when a target uses MFA, and the short-lived read-only database credentials. Everything else in the diagram is in this repository.
  • There is no unit-test box, deliberately. Every project in the execution band — e2e, auth-flows, api, contract, a11y — drives the application from the outside. The framework’s own tests sit inside npm run verify in the generation band, because they gate this repository rather than saying anything about the product.

Section 04The four layers

Locators, actions, fixtures, specs. Each has one job and a hard rule about what it may not do — and each rule is enforced by layer-boundaries rather than by review.

L1 src/targets/<app>/locators/Flat maps of named locators. Also endpoints/ for typed HTTP descriptors and queries/ for named SQL. No logic, no waits, no assertions.
L2 actions/ · api/ · db/Business verbs per medium. Compose L1, return data, assert nothing. Each wraps itself in a test.step() named for intent.
L3 src/fixtures/ + <app>/fixtures.tsThe injectable surface. Framework fixtures are target-agnostic; the target adds its own named actions and data builders.
L4 <app>/tests/{e2e,api,contract,a11y}/Thin specs carrying their case ids as annotations. Every assertion lives here.

What each layer looks like in practice

A locator is a named function of a page. Nothing else:

// src/targets/example-app/locators/sign-in.ts
export const signInLocators = {
  username: (page: Page): Locator => page.getByRole('textbox', { name: 'Username' }),
  password: (page: Page): Locator => page.getByRole('textbox', { name: 'Password' }),
  submit:   (page: Page): Locator => page.getByRole('button',  { name: 'Sign in' }),
  error:    (page: Page): Locator => page.getByRole('alert'),
};

An action composes locators into something a manual tester would recognise, and returns data rather than asserting:

// src/targets/example-app/actions/sign-in.ts
async withCredentials(page: Page, credentials: Credentials): Promise<void> {
  await test.step(`Sign in as ${credentials.username}`, async () => {
    await page.goto('/');
    await signInLocators.username(page).fill(credentials.username);
    await signInLocators.password(page).fill(credentials.password);
    await signInLocators.submit(page).click();
  });
},

/** The error the form reported, or null when it reported none. */
async readError(page: Page): Promise<string | null> {
  const banner = signInLocators.error(page);
  if (!(await banner.isVisible())) return null;
  return (await banner.textContent())?.trim() ?? null;   // returns data, asserts nothing
}

And a spec reads like the test case it implements:

// src/targets/<app>/tests/e2e/expense-approval.spec.ts
test('TC-4907 · An approved claim posts to the ledger @smoke @expenses', {
  annotation: [{ type: 'practitest', description: '4907' }],
}, async ({ authedPage, api, db, expenses, testData }) => {
  // Arrange over the API — seconds, not a five-step wizard
  const claim = await api.expenses.create(testData.expenseClaim({ amount: 250 }));

  // Act in the UI — this part is the actual subject of the test
  await expenses.approve(authedPage, claim.reference);

  // Assert where each fact really lives
  await expect(authedPage.getByRole('status')).toHaveText(/approved/i);
  expect((await api.expenses.get(claim.id)).body).toMatchObject({ state: 'approved' });
  await expect
    .poll(() => db.ledger.entryFor(claim.reference), { timeout: 30_000 })
    .toMatchObject({ amount: 250, type: 'DEBIT' });
});

The rules that hold it together

  • Specs never import from locators/. If a spec needs an element, the missing thing is an action.
  • Actions never assert. Assertions in specs keep intent readable when a human is reviewing generated code at volume.
  • Framework code never imports or names a target pack — see section 09.
  • One target may not import another's code. Swapping targets selects a pack; it does not reuse one.
  • Step titles are named for intent. step-naming rejects "click #submit-btn" and accepts "Submit the expense claim".

Why not Page Object Model

Rationale

POM's open-ended class surface is exactly what makes LLM output drift: given any method on any page object plus raw page.*, a model invents loginPage.loginWithValidCredentials() — plausible, non-existent, and caught only at runtime. A closed vocabulary of typed fixtures and named verbs turns generation into a constrained choice. This is a bet, and it is falsifiable: generate the same ten cases against both shapes and compare.

Section 05The closed vocabulary

One import gives a spec everything it may use. If the verb it needs is not there, the correct move is to stop and ask — not to reach for page.locator.

import { expect, test } from '../../fixtures';   // the only import a spec needs

The target then adds its own verbs. The template pack adds signIn and testData to show the shape; for your application it will be whatever its business language actually is.

The catalog is generated, so it cannot go stale

npm run catalog:build walks the TypeScript AST with ts-morph and writes docs/generated/catalog.md: every exported fixture and every L2 verb — actions/, api/ and db/ alike — with its signature and first doc line. Agents are told to select from that file. CI runs catalog:check and fails if the committed copy has drifted, because a stale catalog lists verbs that no longer exist — precisely the hallucination it exists to prevent.

It reads both idiomatic vocabulary shapes: a plain exported object (export const auth = { … }) and a factory that takes a client and returns one (export function ordersApi(client) { … }). The second is what an HTTP or database vocabulary needs, and missing it would hide that entire surface from the agent — which is why the extraction has its own tests.

What the agent reads

NameSignatureWhat it does
signIn.withCredentials(page: Page, credentials: Credentials) => Promise<void>Submit the sign-in form.
signIn.readError(page: Page) => Promise<string | null>The error the form reported, or null when it reported none.
ordersApi.create(order: NewOrder) => Promise<Order>Create an order and register it for cleanup at the end of the test.
ledgerDb.entryFor(reference: string) => Promise<LedgerEntry | null>The ledger posting for an order reference, or null when nothing has posted yet.

Those rows are the template pack's, verbatim from the generated file. Your application's verbs replace them.

When the vocabulary is missing something

Convention

Stop and say so. Do not invent a helper, and do not work around the gap with a raw locator. A missing verb is a design question, and the answer is usually a new action added deliberately, once — not inlined into a spec that then diverges from the forty others doing the same thing.

Section 06Executable guardrails

Ten custom ESLint rules in eslint-rules/, each with its own tests. These are the framework's real conventions; the markdown is a description of them.

Two rules worth understanding properly

secrets-via-fixture, and its single exemption

Security

Credentials resolve through the secrets fixture, which registers every value with the redaction helper at fetch time. A credential read straight from the environment is one that is not registered, so it survives into a trace, and from a trace into an attachment on a test management system.

Integration tokens do legitimately arrive as job variables — that is how GitLab's secrets: keyword delivers them from Vault. So exactly one file may read them: src/support/env-credentials.ts, whose credentialFromEnv() registers the value on the way through. The exemption is one file rather than one directory precisely so it stays auditable.

Naming carve-outA name ending in _PATH, _FILE, _REF, _SOURCE, _ROLE, _MOUNT, _URL or _ADDR describes where a secret lives, not the secret. References are exactly what an agent is allowed to write.

no-target-coupling, and why it exists

Agnosticism

layer-boundaries stops framework code importing a target pack. This rule stops the subtler version: if (target.name === 'acme-shop') inside a fixture, which is how a framework acquires a special case for the application it was written against — a special case nobody notices until the second application arrives.

Target names are read from config/targets/*.ts at lint time, so adding an application never means editing a rule. The correct way to branch is a declared capability, which says something true of the target and therefore holds for every application sharing the property:

if (target.capabilities.mfa === 'none') …   // yes
if (target.name === 'acme-shop') …          // no — fails the build

Three boundaries that carry weight

  • src/targets/ makes the per-target boundary a directory, not a convention — which is what lets a lint rule enforce it, and what lets config/targets/ be discovered rather than registered.
  • cases/ is the junction. Track A writes into it from a story, Track B fills it from PractiTest, and generation reads only from it. One input format regardless of origin.
  • docs/generated/ is committed, deliberately. The catalog and the run history are both derived, and both are checked into git so CI can diff them and so trends survive artifact expiry.

Section 08Your first spec, start to finish

The intended workflow, whether you are a person or an agent. The order matters: explore before writing, because guessed locators are the single largest source of dead-on-arrival tests.

1

Read the case

Specs implement managed cases, not ideas. Start from cases/<target>/*.yaml — it carries the preconditions, the steps, the assertions and the acceptance criterion it claims to cover.

If the case is vague: run npm run cases:gate. If it fails, send it back with the named gap rather than inventing the missing specifics.

2

Explore the running application

Snapshots go to disk and are read on demand — roughly 4× cheaper in tokens than streaming them through the MCP server, and the reason the CLI is the documented default.

npx playwright-cli open $BASE_URL          # the host from your profile
npx playwright-cli snapshot            # accessibility tree → .playwright-cli/*.yml
npx playwright-cli find "Checkout"     # search the snapshot
npx playwright-cli eval "() => document.querySelector('.item')?.outerHTML"

Write L1 from what the snapshot says, in priority order: getByRole, then getByLabel/getByPlaceholder, then getByTestId. Raw CSS needs a justification comment; XPath is never allowed.

3

Check the catalog before writing a verb

Open docs/generated/catalog.md. If the action exists, use it. If it does not, add it to actions/ — one named business verb, composing locators, returning data, asserting nothing, wrapped in a test.step() named for intent.

4

Write the spec

One import, the case id as an annotation, tags for suite selection, and every assertion in the body. Read it aloud against the case: it should match step for step.

Tags: @smoke runs on every merge request; @auth means the spec must live in a *login|mfa|password.spec.ts file and take page, not authedPage.

5

Let the guardrails answer

npm run lint          # the ten conventions
npx tsc --noEmit      # actions and fixtures fully typed
npx playwright test --grep "SD-012"

Each failure names the rule, the reason and the remedy — written to be actionable by an agent with no other context.

6

Rebuild the generated files

If you added or changed an action or fixture, the catalog is now stale and CI will say so:

npm run catalog:build       # docs/generated/catalog.md
npm run instructions:build  # only if you edited docs/CONVENTIONS.md

Section 09Adding an application under test

The application is configuration. Framework code never imports, names, or special-cases a target — and two lint rules fail the build if it starts to.

Scaffold it, explore it, check it

npm run target:new -- --name=<app> --url=<base-url>   # profile + four-layer pack
TARGET=<app> npm run explore                          # open it, snapshot to disk
TARGET=<app> npm run target:doctor                    # profile vs pack vs credentials
TARGET=<app> npx playwright test --project=setup:auth # prove sign-in works

There is no registration step. Profiles are discovered from config/targets/ — every file there exporting a TargetProfile is a selectable target. That used to be a hand edit to a shared file, and it was the one step in onboarding that reached outside the new application's own directory. It was also the step people forgot, producing Unknown TARGET for a profile sitting right there.

1

Scaffold the profile and the pack

target:new writes config/targets/<app>.ts and the whole of src/targets/<app>/ — locators, actions, fixtures, and the tests/auth.setup.ts that is easy to forget and produces a baffling failure when it is missing. It never overwrites. --with=api,db,contracts,a11y adds the optional layers; the api layer also needs --api-url, because a profile that enables the API capability with nowhere to call is dead on arrival, and the accessibility layer takes --a11y-standard (default wcag22aa).

The capability matrix is the important part of what it writes: it is how every downstream decision is made without anyone naming your application.

export const yourApp: TargetProfile = {
  name: 'your-app',
  baseURL: process.env.BASE_URL ?? PLACEHOLDER,
  environment: process.env.TARGET_ENV ?? 'staging',

  credentials: { source: 'vault', root: 'qa/your-app/pools', accountType: 'workforce' },

  capabilities: {
    mfa: 'totp',              // 'none' | 'totp' | 'email'
    accountPool: 'leased',    // 'static' | 'leased'
    serverState: true,        // does state need cross-test cleanup?
    api:       { enabled: true, baseURL: process.env.API_BASE_URL },
    db:        { enabled: false },
    contracts: { enabled: true, spec: 'src/targets/your-app/contracts/openapi.yaml' },
    a11y:      { enabled: true, standard: process.env.A11Y_STANDARD ?? 'wcag22aa' },
  },

  testIdAttribute: 'data-testid',    // your app's, not the framework's
  hostAllowlist: ['staging.internal'],
  roles: ['submitter', 'approver'],
  suites: ['smoke', 'regression'],
};
2

Explore, then rewrite every locator

npm run explore opens the host from the resolved profile and playwright-cli writes the accessibility tree to disk. Not typing the URL is not ceremony: resolving the profile runs the non-production allowlist check on the way through, so exploration is subject to the same guard as a test run. A typed URL bypasses it.

Every locator in the scaffold is a guess. They are placeholders shaped like the real thing so the file compiles and lints — nothing more. Locator hallucination is the largest single source of dead-on-arrival generated tests, and grounding L1 in a snapshot is the only real fix.

3

Name the business verbs, and expose them

The scaffolded actions/ shows the shape — compose locators, return data, assert nothing. Replace it with this application's real vocabulary, then expose it from fixtures.ts, which is the one file a spec imports.

export const test = framework.extend<YourAppFixtures>({
  claims:    async ({}, use) => { await use(claims); },
  approvals: async ({}, use) => { await use(approvals); },
  testData:  async ({ run }, use) => { await use(buildTestData(run)); },
});

Then npm run catalog:build, so the agent's capability catalog lists the verbs that now exist.

4

Check before you run

TARGET=your-app npm run target:doctor

A profile is a set of claims about an application: it has an API, it uses TOTP, these roles can sign in. Nothing used to check those claims against the pack and the secret store until a spec ran and failed somewhere unhelpful — "No storage state for role 'approver'" when the real problem was a missing auth.setup.ts three directories away.

The doctor reads the profile, looks at what is actually on disk, asks the secret store what it can resolve, and prints the disagreements with the file to fix. It never prints a credential — existence and field names only. Errors block a run; warnings are smells that will not.

What the preflight catches

CodeLevelThe failure it replaces
auth-setup-missingerrorRoles declared but nothing writes a storage state, so every spec taking authedPage fails pointing at the wrong thing
credentials-missingerrorA declared role with no credentials — reported with the exact path that was looked at
api-no-baseurlerrorapi.enabled with nowhere to call; the fixture refuses mid-test
contracts-spec-missingerrorA schema declared in the profile but never vendored, throwing once per spec
db-no-drivererrordb.enabled while no driver adapter exists — a trap, not a preference
totp-needs-vaulterrormfa: 'totp' against a store that cannot issue codes
host-not-allowederrorA base URL its own allowlist does not cover — caught before a browser opens
role-overlaperrorA role listed as both authenticating and non-authenticating
leasing-degrades-silentlywarningA leased pool on a store with no compare-and-swap: every worker quietly shares one identity, which looks fine until two collide
contracts-ready-not-enabledwarningThe document landed but the capability is still off, so nothing validates against it
baseurl-placeholderwarningThe scaffold's reserved host, never replaced
rotation-without-policywarningRotation configured with no password policy — it fails half-way, after changing the account in one place

Each one names what is true and what to do about it; a check that cannot say what to do is a check that gets ignored. They are pure functions over a profile and a description of the filesystem, so all of them are tested without a target on disk, a Vault, or a network.

Rule of thumb: if you find yourself editing src/fixtures/, src/integrations/, src/support/ or tools/ to make a new application work, that is a framework bug. The thing you need is a capability, not a special case.

More than one application in the repository

TARGET selects. Unset, with several to choose from, the browser projects are not built at all and only the framework's own framework project runs — alphabetical order does not get to decide which application gets tested, and npm run verify keeps working the moment a second application is onboarded. Only selection degrades that way: a target that is selected and misconfigured throws, because a suite that quietly skipped itself and reported green is worse than one that failed to start.

What a capability actually controls

CapabilityEffect when off
mfa: 'none'otp.get() throws a stated reason instead of hanging until timeout. The whole of the OTP layer is inert.
accountPool: 'static'No leasing, no rotation, no quarantine. accounts.lease() becomes a plain read.
api.enabled: falseThe api project does not exist, the fixture refuses with a reason, and the report says "not applicable" rather than showing a silent zero.
db.enabled: falseEvery named query fails with the question you should answer first: which facts genuinely need a database assertion?
contracts.enabled: falseNo schema validation hook, no contract project.
a11y.enabled: falseNo accessibility project, and the a11y fixture refuses with a reason rather than reporting a clean sweep it never ran. It carries the standard the application is held to, so turning it on is a statement about the product rather than a preference about testing. Chosen at onboarding with --a11y-standard, overridable per environment with A11Y_STANDARD, and any string is accepted — the doctor spell-checks against the names it knows rather than gating on them, because a standard newer than this repository must never wait on a change to it.

One profile ships: example-app, a template. It is entirely environment-driven and its default host and allowlist both use .invalid, the domain RFC 2606 reserves so that it can never resolve — a profile that ships a guessable hostname is a profile someone eventually points at the wrong environment. Copy it, rename it, and replace both.

Section 10Secrets, sessions and identity

The agent writes the reference; the value resolves at runtime, inside the test process, and is registered for scrubbing the moment it arrives.

How a credential travels

profile.credentials.root          qa/staging/pools
        + accountType             /workforce
        + role, index             /approver/1
                                  ↓
secrets.account('approver')  →  SecretStore  →  Vault KV v2 (or the local store)
                                  ↓
                  registerSecretPayload(...)  ← every value, at fetch time
                                  ↓
                     redact() before any trace, report or attachment leaves

SecretStore is an interface with two implementations. VaultSecretStore speaks HTTP directly — one less binary on a locked-down host — and supports JWT/OIDC, AppRole and token auth, Enterprise namespaces, KV v2 envelope unwrapping, compare-and-swap writes, the TOTP engine and dynamic database credentials. LocalSecretStore exists for the one case where a file is legitimate — an application whose logins are genuinely public, such as a public demo site — reading config/secrets.local.json, and refusing any path outside the selecting profile's own root.

Why there is a local store at all

Sequencing

So that phases 0 to 2 can be proven before a Vault administrator has enabled anything. The demo credentials are public and trivial, and they still go through the secrets fixture on the same path shape as every other target — because the moment one target is allowed to bypass the fixture, the lint rule stops being enforceable and the pattern erodes.

Sessions

Storage state is the default. A setup:auth project signs in once per role and writes .auth/<target>.<role>.json; the e2e project declares a dependency on it so it cannot start first. The framework overrides Playwright's own storageState option with a fixture derived from role, which means test.use({ role: 'approver' }) switches identity while tracing, video and screenshots keep working unchanged.

The exception is its own project. auth-flows matches *login|mfa|password.spec.ts, runs signed out, and auth-project-boundary fails the build if an @auth spec is filed anywhere else or takes authedPage.

Treat a storage state file as a credential. Gitignored, never a CI artifact, never attached to a result, regenerated per run.

Account pools

On a leased target, a worker-scoped fixture takes an account for the life of the worker: one login and one storage state per worker, never two workers sharing an identity. Leasing uses a Vault compare-and-swap write, so two runners starting simultaneously cannot both take account 1 — the loser sees a version mismatch and moves to the next index. Leases carry a TTL so a crashed runner self-heals, quarantined accounts are skipped and never implicitly restored, and exhaustion raises a named error with the role and the counts rather than a timeout ten minutes later.

MFA

One interface, two providers. arm() takes a watermark before the code is triggered; get(mark) accepts only what arrived after it. That is the entire defence against the failure everyone hits — polling the inbox and reading the previous test's code — and it is combined with per-worker plus-addressing so parallel workers cannot read each other's mail. The TOTP provider checks the remaining window and waits for the next one rather than returning a code that will expire between fetch and submit.

Section 11API, contract and data

The layers extend sideways, not downward. actions/ is the UI vocabulary, api/ is the HTTP vocabulary, db/ is the read vocabulary — all L2, all returning data, none asserting.

Schema conformance lives inside the client

The design decision worth understanding: validation runs inside the shared API client rather than as a separate suite. So every API call in every test — including the setup calls inside UI journeys — is a contract check for free, and incidental traffic becomes coverage.

const response = await client.call<Order>(orderEndpoints.create, { body });
// → status checked against the endpoint's expected set
// → body validated against the vendored OpenAPI document
// → drift recorded, and thrown in api/contract projects

Inside a UI journey drift is recorded rather than thrown: failing the journey on a provider's schema change hides the thing the test was actually about. In the api and contract projects it throws, and it reports as its own category — contract drift, not application defect — because the distinction routes the ticket to a different team.

Name it precisely: this is schema conformance, not Pact

Honesty

It catches provider drift after deployment. It does not fail a provider's build before release, which is what consumer-driven contract testing is for. Saying "we already do contract testing" is how a real initiative gets deferred on false grounds.

Database access is deliberately awkward

The hierarchy is a rule, not a preference: assert through the UI if the user can see it, through the API if a service exposes it, and through the database only when neither does. defineQuery() rejects anything that is not a single SELECT — at definition time, not at run time — so the read-only rule is enforced where the query is written. Result sets are capped, parameter counts are checked before the query runs, and a target with the capability off gets an error that states the question to answer first.

Queries are named for the business fact they establish, not the table they read. That naming is not cosmetic: the list is what you send the owning team when they ask which columns the suite depends on, and if it is too long to send, it is too long.

Section 12Authoring: two tracks, one spine

Track A starts at a Jira story and drafts cases. Track B picks up a case already written in PractiTest. Both converge on cases/*.yaml, so there is exactly one place where a case becomes a spec.

The three AI roles never overlap

RoleSeesMust never see

Spec generatorThe case, the catalog, live snapshotsThe story's open questions; its job is to implement the agreed case
Triage agentFailures, evidence, historyWrite access to anything at all

The invention guards are code, not prompting

A model given a thin story does not produce nothing — it produces fluent, well-formatted cases for behaviour nobody specified, and once published such a case looks exactly like a requirement. Three mechanical checks contain it, and all three run after the model replies:

  • Citation. Every case must cite a criterion by an id the story actually contains. One that does not is written to a speculative-* file for a human to triage, never published.
  • Verbatim quoting. acQuoted is checked as a substring of the story. A paraphrase is quarantined, because a paraphrase is how a requirement quietly changes meaning between the story and the case.
  • Coverage, inverted. Every criterion must have at least one case behind it. This is the more useful direction: uncovered AC is what a reviewer cannot spot by reading a list of cases that all look reasonable.

Then the specificity gate runs over what survived, and the cost of the run is reported — because "generation cost has not been estimated" was a real gap, and it is one extra number from an experiment already happening.

Publication is the only irreversible step

npm run cases:push is a dry run unless you pass --publish. It is idempotent on case identity, so re-running updates rather than duplicating; it records provenance in custom fields so "how many of our cases were written by a model?" is answerable; and it never touches a case whose last editor was a human. That last rule is enforced in code rather than documented, because a re-run that silently reverts a tester's correction is the fastest possible way to lose the team's trust in the whole pipeline.

Traceability, hashed at both hops

Jira story ──contentHash──▶ case ──caseHash──▶ spec annotation
  FIN-2210                   #5104            tests/…/SD-012.spec.ts

npm run hashes:check runs in CI and turns silent drift into a visible task: "3 cases derived from FIN-2210 are stale", or "the spec for #5104 tests a previous version".

Section 13Reporting

One data model, three renderings. The reporter's only job is to emit facts; every consumer reads them.

Getting flaky right

onTestEnd fires once per attempt, including retries, so counting statuses there double-counts every retried test. Flakiness is only knowable once all attempts are done, so the reporter collects attempts and aggregates in onEnd using test.outcome() — the API that actually encodes "passed, but not first time".

Two numbers follow from that, and both are in the report: flake rate as a rate, because a test failing 1 run in 3 matters far more than one that failed twice ever; and first-run outcome recorded separately from the final outcome, because a suite that is green only after retries is not green.

The report

Self-contained HTML — inlined CSS and JS, no CDN, opens from a file share with no server. A status band that reads correctly from across a desk, then triage, trend, coverage, applicability, a filterable results table with an evidence drawer per test, and a health band. Status is always a word as well as a colour; AI verdicts are visually marked as distinct from rule-derived ones.

The digest

Outlook renders HTML through the Word engine: no flexbox, no grid, no custom properties, no media queries. So the digest is table-based at 600px with fully inlined styles, a VML-wrapped button, a plain-text alternative part, and no data: images — Gmail strips them and Outlook blocks them. The rich report is linked, never attached; an .html attachment is a standard phishing vector and corporate filters quarantine it.

The subject line carries the verdict so it is triageable from a lock screen, and by default the digest only sends on failure or a change of state — a nightly mail that is green 90% of the time trains its recipients to filter it.

Trend history

Trends need retained history and CI artifacts expire, so the decision was made rather than deferred: each run appends one summary line to docs/generated/run-history.jsonl, keyed by target, environment and branch. A database is not needed for hundreds of runs a year, and choosing one is how this stalls. "Newly failing" and "newly fixed" are computed against the previous run in the same lane — a trend that mixes environments is noise.

Section 14Triage

The most valuable component, and the one most likely to be built wrong — because the obvious implementation is to hand every failure to a model and ask what happened.

  1. Pass 1ClusterNormalised error + failing step + window
  2. Pass 2RulesDeterministic classification, no model
  3. Pass 3ModelOnly what the rules could not settle

Clustering first does three things at once: it stops forty Jira tickets being filed on a bad night, it cuts cost by roughly the clustering factor, and it makes the answer more accurate — because breadth is itself the evidence for an infrastructure cause, and a per-test view cannot see it. Forty tests failing with the same connection error collapse to one cluster; a test showing an assertion mismatch stays separate.

What the rules settle without a model

SignalConclusion
Passed on retryflaky — by definition, not inference
ECONNREFUSED / DNS / TLSnetwork-infrastructure
Response failed schema validationcontract-drift → provider team
5xx on a valid requestapplication-defect, never a locator
Vault or mail adapter threwdependency
Every executed test failed at authenvironment-config
Fingerprint matches an open defectknown issue — link, do not re-file

The guardrails on the model

  • Advisory by default. It annotates the report. Filing is behind JIRA_AUTOFILE, and the model itself is behind TRIAGE_AGENT_ENABLED — both off.
  • Every claim cites evidence. A verdict with an empty evidence array is rejected by the validator and replaced with unclassified, needs human review. That is what makes the output reviewable rather than merely confident-sounding.
  • Three confidence levels, never a percentage. A model's "92% confident" is not calibrated, and printing it as one manufactures trust the number cannot support.
  • Low confidence is a valid answer, and an agent that throws routes the cluster to a person rather than failing the run.
  • Evidence is scrubbed before it leaves the process, and the report marks AI verdicts as distinct from rule-derived ones.

Measure it. Record the agent's category alongside the human's eventual verdict and publish agreement per category. A triage agent nobody trusts is worse than none, because it adds a step without removing one.

Section 15Rotation, quarantine and healing

Three maintenance capabilities, each dangerous in its own way, each constrained accordingly.

Password rotation — the order is the design

Most dangerous

Everything else in this framework fails safe. Rotation writes to a live system, and its failure modes lock accounts out.

lease exclusively → change in the application → VERIFY by authenticating
                  → write a new KV v2 version → invalidate storage state → release

Vault-first would leave an account nobody can use and a credential store that lies about it. So nothing is persisted before it has been verified, and a failure at any step quarantines the account rather than retrying blindly. Blackout windows and jitter are enforced inside the runner, not in the pipeline schedule, so a manually triggered run cannot bypass them — rotating an account mid-suite produces authentication failures that look exactly like application defects.

Also handledPassword policy generation that satisfies the real rules, the application's minimum-age constraint, and deterministic per-account jitter so a re-run picks the same day rather than drifting earlier every cycle.

Quarantine — visible, not hidden

Hygiene

config/quarantine.json is committed and every entry needs a reason, a date and a named owner. The report shows the list with its age, so an entry that has been "temporarily" quarantined for four months is visible rather than forgotten. Candidates are ranked by flake rate over a window, and the ranking refuses to judge from too little history. Nothing adds to the file automatically — quarantining is a reviewed decision.

Healing — a brief, not an edit

Leashed

A healer that "fixes" a test to match newly-broken behaviour destroys the test's reason for existing. So npm run heal changes no source file. It produces a brief: which failures are safely healable, and which are escalated with the reason.

Locator and timing repairs only. A changed assertion or expected value is always escalated — if a button's accessible name changed because someone broke the i18n bundle, healing the locator hides a real defect and the suite goes green on a broken build. A triage verdict of anything other than heal also blocks the candidate. Whatever comes back opens a merge request; it never pushes to a protected branch.

The drift harness

The healer needs drift to repair, and a stable application never drifts. So drift is induced deliberately: an init script installs a MutationObserver before any application script runs, stripping the test-id attribute or rewriting accessible names as elements appear.

It mutates the rendered DOM, not the HTML response — and that distinction is load-bearing. A client-rendered application ships a near-empty document and builds the page in JavaScript, so a response rewriter silently does nothing and produces a "the healer works" result that means nothing. The shipped specs assert that the drift actually landed, for exactly that reason.

Section 16The CI pipeline

Six stages in .gitlab-ci.yml. Every npm script it calls exists and runs; the pipeline shape itself has never executed, because no GitLab instance has been available.

Three decisions worth noting

  • One merge job, for two reasons. PractiTest allows 30 calls a minute, so N shards posting independently blows the limit on the first real night — and flaky status is only knowable once every attempt across every shard is accounted for. The two constraints want the same architecture.
  • Vault via id_tokens, not AppRole. GitLab mints a signed JWT per job; there is no secret to deliver, wrap or rotate. The real win is bound claims: a job on a fork's feature branch cannot read staging credentials even holding a valid token.
  • Reporting never fails the build. Every publish job is allow_failure: true, and the tools degrade to a warning plus a retained artifact. A reporting outage must not turn a green suite red.

Before it runs for real: pin PW_VERSION to package.json, have a Vault admin enable the JWT backend and role, replace every <placeholder>, and confirm GitLab Pages is enabled or switch the report link to a job artifact URL.

The project is called framework for exactly that reason: a project named unit sitting beside e2e and api reads as a claim nobody here is making.

Note the distinction. "No fakes in CI" in the plan is about test environments — the framework provisions nothing and talks only to real running systems. Unit-testing an adapter against a fake is the opposite of that, and is explicitly what the plan asks for.

Section 19What is proven, and what is not

The distinction matters more than any line count, so it is stated plainly rather than implied by a green badge.

Verified by running it

Proven

The four layers and all ten lint rules. The target profile mechanism and session setup. The case format, quality gate, capability catalog and instruction sync. The Vault adapter, account-pool leasing under concurrency, both OTP providers, and rotation ordering — against an in-process Vault. Redaction, including a canary leak test. The shared API client and schema conformance, and read-only query enforcement. The PractiTest and Jira clients against in-process fakes, including rate limits and Data Center's Bearer-auth behaviour. Track A's invention guards. The run model, the HTML report and the digest's Outlook constraints. Triage clustering, every rule, and the verdict validator. The healing brief's refusal to touch assertions. And the drift harness — against a live application.

Not proven, and not provable from here

Open

No real Vault, PractiTest, Jira, mail tool, GitLab runner or internal application has been reachable. Every adapter is written against its documented contract and exercised against a fake that encodes that contract — first contact with the real systems will still find things. .gitlab-ci.yml has never executed. And the generation hit rate — the plan's own riskiest assumption — is unmeasured, because measuring it needs the real cases and the real target.

A reference target's roleThe framework was proven end to end against a live public site, and that work — including a triage ground-truth fixture and the drift harness — is on the saucedemo/extensive-coverage branch. What it demonstrates is that the wiring works. That application had no MFA, fixed public users, no service API and a DOM that never changes, so it says nothing about whether this design survives pools, rotation, contract drift or real UI drift. Every phase exit involving those must be met against your own application.

Deliberate deviations from the plan

Two

The canonical reporter moved earlier. The plan puts run-result.json in phase 5; it was built during phase 3 because the PractiTest publisher reads it, and having two sources of run facts even temporarily is the exact failure the single model exists to prevent.

Allure is documented, not installed. The plan recommends emitting Allure results alongside the canonical JSON. It is not wired up, because it cannot be verified without a real run history to feed it — and an unverified dependency in a template is a liability rather than a feature.

Section 20Gotchas and house conventions

Things that will catch you once

  • --reporter on the CLI replaces the config list. Running npx playwright test --reporter=list silently skips the run-result reporter, so no run-result.json is written. Omit the flag when you want the full reporter set.
  • Specs import from ../../fixtures — the target's own fixture file, not @playwright/test. That import is the closed vocabulary.
  • The seed spec is not a test. tests/seed.spec.ts is the template Playwright's generator starts from; no project's testDir picks it up, and the lint rules exempt it.
  • Edit docs/CONVENTIONS.md, never the three generated files. CLAUDE.md, AGENTS.md and copilot-instructions.md are byte-derived and CI fails on drift.
  • Adding an action means rebuilding the catalog. catalog:check will fail otherwise, which is the point.
  • .auth/ never leaves the machine. It is gitignored and excluded from CI artifacts; a storage state file signs you in as that account with no password and no MFA.
