Application-agnostic test automation

One framework, any application under test.

The application is configuration, not code. Drop a profile in, drop a four-layer pack in, and the same fixtures, reporters, triage rules and publishing paths work against it — or take it back out and leave the repository exactly as it was.

01

Start here

Five minutes to a green build, and the one command you will run more than any other. 

# install, then prove the framework itself is sound
npm install
npm run verify

verify is lint, typecheck, the generated-file checks and the framework's own test suite. It is deliberately buildable with no network, no credentials and every demo application down — that is what makes it the command CI and every contributor can run. It does not touch an application under test.

The loop

Everything in this repository is arranged around one feedback cycle. Write, run the guardrails, read structured errors, repair. Anything a human has to catch by eye is a convention that has not been finished. 

write  →  npm run lint && npx tsc --noEmit && npx playwright test  →  structured errors  →  repair
Why it matters

Every rule in this handbook is enforced by a lint rule, a type or a failing test wherever that is possible. Documentation is the fallback for the rest — if you find a rule here that a machine could have checked, that is a bug in the rule, not in the person who broke it.

Selecting an application

TARGET selects which application a run is pointed at. With nothing selected and several to choose from, only the framework's own project builds — alphabetical order does not get to decide which application gets tested. 

TARGET=acme-shop npx playwright test          # that application's suites
npx playwright test --project=framework      # the framework testing itself
npm run suites:live                          # every onboarded application, live
02

Rule zero

Fix the framework, never the application's pack. This is compulsory, and it outranks every other rule here.

Rule zero

When something is broken, flaky or hard to diagnose, the fix goes into the application-agnostic framework and is validated end to end from there — through onboarding, target:doctor, and a run. Never troubleshoot by hand-editing config/targets/<app>.ts, anything under src/targets/<app>/, or an application's specs and docs.

A target pack is an output. npm run onboard writes it, target:doctor checks it, healing and triage act on it. Editing the output fixes one application and leaves the generator, the preflight and the rules exactly as wrong as they were — so the next application onboarded meets the identical problem, and nobody finds out until it does.

The question to ask about any fix is “which mechanism produced this artifact, and is that mechanism right?”

Symptom in a packWhere the fix belongs
A scaffolded locator that cannot matchThe probe that derives it, or the scaffold template
A profile value that is wrong or missingThe onboarding step that reads it, and target:doctor
A failure nobody can diagnose from the messageThe action or reporter that produces the message
A condition a run should have caught earliertarget:doctor preflight, healing, or a triage rule
A verb a spec needs and cannot findA new action, added deliberately

The worked example

A sign-in error banner was read with getByRole('alert'), which matched nothing on an application whose banner carries no role. readError returned null, so a failed run reported “the form reported no error … check the signed-in locator rather than the credential” while the application was saying “Account locked, too many failed attempts” on screen.

Editing that one target's locator would have taken a minute and taught the framework nothing: the scaffolder would still emit the same guess for the next application, the doctor would still not preflight it, and triage would still have no rule for a lockout. Reverted, it became three framework mechanisms instead of one patch.

The one exception

Authoring new coverage. Specs, and the locators and actions they need, are written in the pack by design — that is what a pack is for. The rule governs troubleshooting: if you are changing a pack to make an existing failure stop, stop and find the mechanism.

If the framework genuinely cannot express the fix, that is the finding: raise it as framework work and say what is missing. “It was quicker in the pack” is not a reason, and neither is “only this application has the problem” — the second one is nearly always false and is exactly how it stays hidden.

03

A defect in the application is a failure, and it stays one

Never change this framework to make an application's defect pass. A red spec naming what broke is what the suite is for.

Tailoring a locator, loosening an assertion, adding a retry or teaching a verb to tolerate wrong behaviour all convert a finding into silence, and the team stops hearing about a real defect. Two things look alike from a stack trace and are not alike at all:

Which is it?Whose problemWhat to do
A defect in the application — it does the wrong thing, or does it unreliably Theirs Report it. Leave it failing. File it. A spec that fails every run for a known, filed defect is doing its job.
Contention this suite creates — two workers on one identity, a spec mutating data another asserts on, a fixed wait racing a render Ours Fix it here.

Ask which one it is before touching anything, and say which in the commit. The evidence is usually cheap: run the failing thing with nothing else running. If it still fails, no change in this repository will honestly fix it.

A known failure is declared, never inverted

test.fail() inverts the whole test, so a spec marked that way is reported as passing the moment it fails for some other reason — an outage, a moved locator, an expired session. On an application with known defects, which is also the kind that falls over upstream, that is the normal case. It happened: two specs marked for defects a bank genuinely has were green through a whole run in which neither reached a transfer form. 

annotation: [
  { type: 'practitest', description: 'PB-2-01' },
  { type: 'known-failure', description: 'a bank accepted a negative transfer' },
]

Say what the failure should contain and leave the assertion alone. npm run suites:live then reports it three ways rather than one: still failing as declared expected, failing for something else ordinary failure, or passing marker can go. The known-failures-declared lint rule refuses test.fail().

Three recorded exceptions, and none of them is a deleted assertion

InstrumentForWhat keeps it honest
ContractWaiverAccepted drift between a published document and a running serviceA reason and a review date the doctor enforces; waived drift is still counted
A11yWaiverAn accepted accessibility exceptionScoped by urlPattern and selector; waived nodes still counted, so three cannot quietly become ninety
parkedAn application that cannot be tested at allA reason and a review date; suites:live reports it as parked rather than running it
Parking is not for a suite that fails

It is for an application that cannot be tested. A defect in our specs is ours to fix, and a defect in the application is a finding worth keeping red until somebody decides otherwise — deliberately, in the profile, with a date.

04

The four layers

Each layer has one job and a list of things it may not do. The boundaries are enforced by layer-boundaries, not by review.

L1
src/targets/<app>/locators/ · endpoints/ · queries/

Named locators, typed endpoint descriptors, named parameterised SQL.

May not contain logic, waits or assertions. Queries may not write anything, ever.
L2
src/targets/<app>/actions/ · api/ · db/

Business verbs, typed HTTP clients, a read-only query vocabulary. They compose primitives and return data.

May not assert outcomes. The db layer may not write.
L3
src/fixtures/ · src/targets/<app>/fixtures.ts

The injectable surface. Everything a spec receives arrives here.

May not name a host or a selector.
L4
src/targets/<app>/tests/

Specs. Every assertion lives here. A spec body should read aloud to a manual tester and match their test case step for step.

May not import from locators/.

Rules that execute

  • Specs never import from locators/. If a spec needs an element, the missing thing is an action.
  • One target may not import another target's code.
  • Framework code (src/fixtures/, src/integrations/, src/support/, tools/) may not import a target pack, and may not name one.
  • Specs call typed clients — no raw request.*, no fetch, no inline SQL.

What L3 actually hands a spec

Fifteen framework fixtures, available in every spec whichever application is under test, plus whatever the pack's own fixtures.ts adds on top. A fixture for a disabled capability skips the test with a stated reason rather than hanging until timeout.

This table is a copy; the generated one is the truth

docs/generated/catalog.md lists these and every verb each pack exposes, rebuilt by npm run catalog:build and checked in CI by catalog:check. Read it before writing a spec — it is the answer to “does the verb I need already exist?”

Why not Page Object Model

A page object mixes all four jobs into one class: it holds selectors, composes behaviour, waits, and often asserts. That is why page objects grow into god classes nobody can safely change. Splitting the four means each has a rule a machine can check.

When the vocabulary is missing

If the action, fixture or client you need does not exist in docs/generated/catalog.md: stop and say so. Do not invent a helper, and do not reach for page.locator to work around the gap. A missing verb is a design question — the answer is usually a new action, added deliberately, once, rather than inlined into a spec that then diverges.

The catalog is generated by npm run catalog:build, so it cannot go stale, and catalog:check fails CI if it drifts.

05

Locators

Locator hallucination is the largest single source of dead-on-arrival generated tests. Exploration is the only real fix.

#StrategyVerdict
1getByRole(role, { name })how a user and a screen reader find it
2getByLabel, getByPlaceholder, getByTextgood
3getByTestIdattribute declared per target
4Raw CSSonly with a justification comment
5XPathnever

Scope a locator to its container

Applications reuse test ids across pages more often than the priority order implies. An unscoped locator that matches on two pages does not fail — it answers the wrong question with a plausible result. 

// no  — matches cart rows AND listing cards, depending on the page
items: (page) => page.getByTestId('inventory-item'),
// yes — unambiguous wherever it is called
items: (page) => cartLocators.list(page).getByTestId('inventory-item'),
Measured, on a real application

getByRole('table') is not “the cart” — it is whichever table is on screen. On one application it matched the product specifications table on the page a cart click started from, so the action waited for “a table”, found the one it was already looking at, decided the cart had arrived, and read five rows of specifications as cart lines. No error and no timeout: an empty cart and a plausible total. Scope to the thing that makes the answer unambiguous — the cart is the table containing the total cell.

Ground locators in the accessibility tree, not a DOM dump

The snapshot npx playwright-cli snapshot writes is what getByRole and a screen reader both read. A DOM dump is not: a script that fell back to the placeholder attribute reported Your email for a field whose accessible name is Email address *, and every locator written from it failed as a bare fifteen-second timeout on a field plainly on screen.

The same rule applies to values, not only to selectors. A country chosen from memory — Netherlands — matched nothing in a list using UN naming (Netherlands (the)). selectOption with a label that matches nothing does not fail fast: Playwright retries the whole action and times out reporting “waiting for element to be visible and enabled”, which describes the select rather than the missing option.

Derive internal identifiers; never write them down. If a vocabulary needs an id, slug or key belonging to the application, read it from the running application. A transcribed internal id is a hallucinated locator wearing a different hat, and it fails silently. 

npm run explore                    # opens the profile's host — never a typed URL
npm run explore -- /checkout       # a path on it, resolved against the profile
npx playwright-cli snapshot        # accessibility tree to disk as YAML
npx playwright-cli find "Checkout" # search the snapshot
Cheaper than the MCP server

Snapshots are written to disk and read on demand, which is roughly 4× cheaper in tokens than streaming them through the MCP server. The MCP server is installed too — reach for it when a human is interactively poking at a stubborn page.

06

Waiting

Wait for the fact, not for the clock and not for the network.

  • No waitForTimeout. No hand-rolled sleep. Enforced by no-hard-waits.
  • Web-first assertions (await expect(locator).toHaveText(…)) wait for you.
  • For genuinely asynchronous facts — a batch posting, a queue — use expect.poll(fn, { timeout }). It is the only acceptable answer to eventual consistency, and it fails as a clear assertion rather than a hung test.
Locator.count() does not wait

Every other read auto-waits; count() answers for the DOM as it is at that instant. An action that returns a count must first anchor on something that does wait, or it reports a truthful zero for a table that has not rendered — and the assertion then reads “expected > 0, received 0”, which points at the application.

networkidle is the wrong instrument and this repository has the scar: it returned while a removed cart row was still in the table. row.waitFor({ state: 'detached' }) waits for the thing the step was actually about.

07

Specs

One spec per managed test case, titled so a product owner can read the report. 

import { expect, test } from '../../fixtures';   // the only import a spec needs

test(
  'SD-012 · Checkout totals include tax @smoke @checkout',
  {
    annotation: [
      { type: 'practitest', description: '5104' },
      { type: 'jira', description: 'FIN-2210' },   // optional
    ],
  },
  async ({ authedPage, inventory, checkout, testData }) => {
    const items = testData.catalogItems({ count: 2 });

    await inventory.open(authedPage);
    await inventory.addToCart(authedPage, items.map((i) => i.name));
    const totals = await checkout.completeThroughOverview(authedPage, testData.customer());

    expect(totals.tax).toBeCloseTo(totals.subtotal * testData.taxRate, 2);
  },
);
  • Title: <case ref> · <what it proves> @tags.
  • Every spec carries a practitest annotation — require-case-id. The contract project is exempt: it verifies a published schema, not a scripted case.
  • Tags are the suite selectors. @smoke runs on every merge request.
  • No test may depend on another test having run first.

Step titles are the report

test.step() titles become the narrative a product owner reads. Name them for intent, never mechanics — step-naming enforces it. 

await test.step('Submit the expense claim', ...)   // yes
await test.step('click #submit-btn', ...)          // no

What kind of test goes where

This suite does not contain unit tests. A unit test reaches into the code under test; Playwright drives an application from the outside, and the two are different jobs done with different tools by different people.

KindWhereProjectAsserts
Functional / end-to-endtests/e2e/e2e, auth-flowsA user journey through the UI
Integrationtests/e2e/, tests/api/e2e, apiA journey spanning UI, service and data
Contracttests/contract/contractA running service against its published schema
Accessibilitytests/a11y/a11yThe application against the standard its profile declares
Performance budgettests/e2e/, tagged @performancee2eA journey finishes inside a stated ceiling
Ground truth for triagetests/triage-fixture/triage-fixtureSpecs written to fail a stated way

tests/framework/ is a separate thing: the framework testing itself — the lint rules, the adapters against in-process fakes, the reporters, triage, onboarding. It runs in the framework project, needs no browser, no network and no target. It is deliberately not called unit, because a project of that name sitting beside e2e reads as unit-testing the application, which is not what any of it does.

Five kinds of coverage

An application is not covered by happy paths alone. target:doctor reports which of the five a pack is missing, and app:journey fails the coverage stage for it.

KindTagAsks
Happy path@smokeDoes the thing work at all?
Negative@negativeDoes it refuse what it should refuse?
Idempotency@idempotencyDoes doing it twice do it twice?
Audit@auditWas the change actually recorded, on a second surface?
Boundary@boundaryWhat happens at the edges?
An audit needs a second surface

Do not tag a reload as an audit. If an application's cart lives in per-tab sessionStorage and its API is a read-only catalogue, there is nothing to ask — and a spec that reloads the page would go green having proved nothing. Accepting four of five kinds honestly beats five dishonestly.

Performance: budgets, not load testing

Load and performance testing are refused — they need different tooling and a dedicated environment, and numbers from a shared runner under unknown contention are not actionable. A budget is in scope. 

expect(elapsed, `the listing took ${elapsed}ms against a ${budget}ms budget`)
  .toBeLessThan(budget);

Keep it loose — a tight budget on a shared runner is a flake generator, and a flaky performance test teaches a team to ignore performance tests. A budget met by an empty page is not a budget met: assert the content arrived, then assert the time.

08

Onboarding an application

Two ways in, onto the same scaffolder. The intended outcome is that setup:auth passes with no file edited by hand.

The dashboard, which is the shorter one

npm run onboard        # opens a local page; reads the application, then writes everything

It drives a browser at the running system and fills in what a person would otherwise have to look up: which attribute getByTestId reads here, the accessible names on the sign-in form, and whether the service publishes an OpenAPI document. It then writes the profile, the pack, the vendored contract document and the credential entries in one go, and offers to sign in once to prove the locators work — which also derives signedInMarker, the one locator that cannot be read from a page at rest.

The wizard reveals one step at a time behind a stated overview, so a step that cannot be reached yet is not on the page. What it cannot read, it says so about, rather than guessing.

The CLI, which does the same job without a browser

npm run target:new -- --name=<app> --url=<base-url>   # profile + four-layer pack
TARGET=<app> npm run explore                          # open it, snapshot to disk
TARGET=<app> npm run target:doctor                    # profile vs pack vs credentials
TARGET=<app> npx playwright test --project=setup:auth # prove sign-in works
On Windows

Run the CLI form from bash — npm's PowerShell shim eats the -- separator and the flags never reach the script. npx tsx tools/new-target.ts --name=… --url=… works in every shell, and the tool says so when it happens.

--with=api,db,contracts,a11y adds the optional layers; the api layer also needs --api-url. There is no registration step — profiles are discovered from config/targets/, so a new file is selectable the moment it lands. Nothing is ever overwritten.

Then the work that cannot be generated

  1. Credentials at <root>/<accountType>/<role>/1 — Vault for anything real, config/secrets.local.json only where they are genuinely public.
  2. Rewrite locators/ from the snapshot npm run explore produced. Every locator in the scaffold is a guess.
  3. Name the real business verbs in actions/, and expose them from fixtures.ts.
  4. Specs in tests/{e2e,api,contract,a11y}/, then npm run catalog:build.
The whole surface

If you find yourself editing anything under src/fixtures/, src/integrations/, src/support/ or tools/ to make a new application work, that is a framework bug: the thing you need is a capability, not a special case.

The preflight

target:doctor checks the profile's claims against what is actually on disk and what the secret store can resolve. Every finding names the file to fix. Errors block a run; warnings are smells.

It catchesBecause
An enabled API with no base URLThe capability is a claim the profile cannot honour
A declared role with no credentialssetup:auth would fail minutes later, far from the cause
A missing auth.setup.tsNo session would be established for any role
mfa: 'totp' against a store that cannot issue codesEvery sign-in would hang on a code nobody can produce
A leased pool that will silently degrade to a shared loginSilent degradation is the failure mode this whole repository refuses
A waiver or parking whose review date has passed“For now” must not become “forever”
Missing coverage kindsA suite of happy paths has never been told no
A worker cap nobody has measuredSee state the suite does not own
No tests/triage-fixture/Triage is never exercised for that application

Keeping a pack current

A scaffolder improvement reaches applications onboarded afterwards and no others — so the fix lands everywhere except where it was needed. npm run target:upgrade regenerates the pack in memory and reports, file by file, how far what is on disk has drifted. It reports rather than rewrites: a pack is half generated shape and half somebody's work, and the second half is the entire point of a pack.

The exception is a line the template owns, marked // @template:<key>. Only those move. Delete the marker and the line is yours — which is the documented way to keep a local change, and the reason the tool will never add a marked line a pack does not have: it cannot tell “never had this” from “removed it on purpose”.

09

Taking an application back out

The one destructive operation here, so it is built the other way round from the scaffolder. 

npm run target:remove -- --name=<app>                   # plan only, removes nothing
npm run target:remove -- --name=<app> --confirm=<app>   # actually remove it

It removes the four places a target leaves something — the profile, the pack, the credential entries and the stored sessions — and nothing else. Framework code is never touched. It plans and reports before it removes anything, says how many of the files git has never seen and therefore cannot bring back, and does nothing at all until the target's own name is typed back. A confirmation a stray click can satisfy is not a confirmation.

Why this makes main pointable at a live application

Try one, drive it, and put the repository back the way it was, with no branch to move between. Afterwards, with nothing selected, only the framework project builds and npm run verify keeps passing. Run npm run catalog:build afterwards — the tool reminds you.

Nothing outside config/targets/ may name a host, and framework code branches on declared capabilities, never on a target name.

11

Secrets and sessions

The agent writes the reference, never the value.

  • Credentials resolve at runtime through the secrets fixture.
  • No process.env for credentials anywhere — secrets-via-fixture. The single exception is src/support/env-credentials.ts, which registers every value it reads for redaction.
  • No process.env at all inside a target pack: base URL, credentials and capabilities all arrive through the target and secrets fixtures.
  • Never log a credential, never write one to disk, never copy one into a snapshot or an attachment.

Where a credential can live

LocationWritable by the toolUse for
VaultnoAnything real. The token is ambient and never typed into a page.
config/secrets.private.jsonyes — the defaultGitignored. Where onboarding writes what you type.
config/secrets.local.jsonyes, deliberatelyTracked by git. Only for credentials an application publishes itself.
The names read backwards, and it has bitten people

secrets.local.json is the one git tracks; secrets.private.json is the gitignored one. Onboarding defaults to private, and the default is where the safety lives — anybody who does not read the section still must not commit a password.

Your own Vault

The dashboard lets you point the framework at your Vault by address, KV mount and path shape, and Check the connection resolves one path server-side and reports the field names it holds. It uses describe rather than read, so it cannot return a value and no flag changes that. No field on that page holds a secret — a URL, a mount and a path template are configuration; a token, a secret_id or a password is not, and none of them gets a box.

Vault mounts KV v2 at secret/ while this framework defaults to kv. That is the first thing to check when a connection resolves nothing.

Sessions

  • Storage state is the default. Only @auth-tagged specs drive a login form.
  • @auth specs live in *login|mfa|password.spec.ts so the signed-out auth-flows project picks them up, and they take page, never authedPage — auth-project-boundary.
  • A storage state file is a live credential. Gitignored, never a CI artifact, never attached to a test result, regenerated per run.
12

State the suite does not own

The failures here never look like contention. They look like a 409, or a cart with one item too many, landing on whichever spec lost the race.

  • A vocabulary must be able to express every state the application has. A cart reader that could only describe a non-empty cart made the spec that empties the cart fail at the step confirming it had worked.
  • Never assert on data the spec did not create. “The seeded customer has order history” passes until the account behind the role changes, then fails for a reason unrelated to what it tests. Place the order you assert about.
  • Everything created gets cleaned up, tagged with run.runId.
  • Assert through the UI if the user can see it, through the API if a service exposes it, and through the database only when neither does.

Worker indices repeat across projects

api worker 0 and contract worker 0 pick the same slot. Neither the worker ceiling nor partitioning on parallelIndex prevents that — both bound how workers are numbered, and this is two projects holding the same slot number at the same time. That is what authFlowAccount is for: it reserves an account for the signed-out project and withholds it from every worker.

serverState answers two questions

It says “data this suite creates needs cleaning up” — and workerCeiling also reads it to decide whether two workers may share an account. So serverState: true with no pool caps a target at one worker: the whole suite runs serially, and declaring a pool of three is what buys the parallelism back, which is backwards from how it reads.

Measured

Four of the first five applications onboarded here declared serverState: true with no pool and ran serially — every one still carrying the scaffolder's // does state need cross-test cleanup? comment verbatim. Nobody had answered a question the scaffold asked, and nobody knew it set the worker count.

Say which you mean. sharedIdentitySafe: true keeps serverState about cleanup and lifts the cap; leaving it unset keeps the cap, which is the safe default and stays the default. Answer it with a measurement, never a guess. 

npm run pool:measure -- --target=<app> --runs=5   # control at the cap, experiment above it

The command runs the suite at the ceiling the profile imposes and again above it with every worker on one identity, and reports both arms. It declines to conclude, deliberately: a failure under one identity is evidence only if the failing spec shares that identity, and a background failure rate is indistinguishable from contention unless you measure both. target:doctor warns while the question is unanswered, and stops once the profile says either way — “yes, the cap is earned” is an answer worth recording, because it stops the next person re-measuring it.

Negative authentication spends the account's lockout budget

Two specs asserting “a wrong password is refused” locked the shared account every other spec signed in as, and twenty-one unrelated tests failed across five features. The lockout counter turned out not to be per-account either.

Declare sharedEnvironment: true in the profile of a deployment shared with strangers, and no-lockout-on-shared then refuses a real account's username paired with a made-up password — the shape that actually spends the budget.

Negative authentication itself stays

The narrowness is the point: a framework that quietly stopped running tests would be worse than the mistake it prevents. Two identities cost nothing and both are already in use — an address nobody registered, unique per run, and an account the application publishes in order to refuse it, signed in with its own real credential. Neither generates a failed-password attempt against an identity anyone else is using.

13

Accessibility

A capability, not a tag — “is this application held to WCAG 2.2 AA?” is a property of the application, and a suite with no stated standard argues about every finding.

  • The a11y fixture runs axe against the rule tags the profile's standard resolves to, applies the profile's waivers, and returns findings. It asserts nothing: “no critical violations” and “none at all” are different products' answers, and that call belongs in a spec a reviewer can read.
  • WCAG conformance is cumulative. wcag22aa means every A and AA criterion from 2.0 and 2.1 as well — testing only the criteria 2.2 added would be a much smaller claim wearing the same name.
  • scan.incomplete is not a pass. Those are checks axe could not decide, and scan.undecided names which — a count alone gives a reviewer nowhere to go.
  • Scan a page a user actually reaches. Landing pages pass nearly everywhere; the dialogs, tables and multi-step forms are where the problems are.
The worst result this suite can produce

A green scan of a page that had not finished rendering. On a single-page application the document loads long before the application renders. Measured on one dashboard: one waived violation immediately after goto, against seventeen across four rules, four of them critical, once the tree went quiet. A false green here is worse than no accessibility suite at all, because somebody reads it as evidence.

Two guarantees, because one was not enough

FlagSaysFalse when
scan.settled The DOM stopped changing before axe ran — a MutationObserver, not load and not networkidle. The page never went quiet. A clock or a carousel will do that forever.
scan.stable Two consecutive scans agreed on what they found. They never agreed inside the attempts allowed.

Quiet is a proxy; agreement is the fact. Under contention a page between render phases is easily still for the quiet period because it is starved or waiting, not because it has finished — and the scan then answers for a shell with settled: true, because by its own definition it had settled. Measured: one application's landing page was green three times out of three run alone, and red under full-suite load with [critical] label on three nodes.

So the fixture scans, settles and scans again, and accepts the findings only when two agree. Raising the quiet period is not the fix: it widens the window without improving the signal, slows every scan on every application, and still loses whenever contention is worse than the number somebody guessed. A spec that scans and never reads stable is refused by a11y-scan-stability.

Waivers

A permanent exception is a waiver in the profile, with a reason and a review date — never a deleted assertion or a disableRules that outlives the pull request. urlPattern and selector are what keep a waiver from being a blindfold: a bare rule id suppresses that rule everywhere, including on pages added next month. The scan still counts waived nodes, so an exception accepted for three cannot quietly become ninety, and target:doctor reports one whose review date has passed.

The standard is chosen at onboarding (--a11y-standard=, default wcag22aa) and overridable per environment afterwards (A11Y_STANDARD). Any string is accepted — target:doctor warns when it does not recognise one, which catches a typo without holding a target to the list this repository happens to know. WCAG 2.2 became a Recommendation in 2023 and 3.0 is in draft, and adopting a newer standard must never require an edit to framework code.

“Run it end to end” means all of it

The suite is one stage of six. Anything short of this list is a partial run and should say which stages it skipped. 

npm run app:journey -- --target=<app>
1

Onboarding

The pack exists and target:doctor --sign-in passes — a credential that resolves and signs in.

2

Stories or cases

A story pulled from Jira, or cases pulled from PractiTest. The suite is traceable to something a person asked for.

3

Coverage

All five kinds present: happy path, negative, idempotency, audit, boundary.

4

Run

The live suites execute against the real deployment.

5

Triage

A run containing a real failure, clustered and classified. A green run exercises none of triage.

6

Publish

Results pushed back to PractiTest, and the report posted to Teams and sent by email.

Stage 5 is the one people skip

Triage classifies failures, so a green run exercises none of it. An application is not end-to-end tested until it carries a triage ground-truth fixture and npm run triage:measure has scored the rules against it. A green suite plus a green triage report is two claims where only one was checked.

None of this requires owning Jira, PractiTest, Teams or a mail relay. npm run fakes:serve stands all four up locally and prints the environment to export — and seeds them from the specs on disk, so a newly onboarded application is covered with no change to the tool. Real instances change nothing about the journey; they change whose channel it lands in.

16

Triage

Cluster the failures, settle what rules can settle, and decline the rest. A rule that invented a category would be the actual defect. 

npm run triage:cluster   # group failures that share a cause
npm run triage:rules     # settle what a rule can settle
npm run triage:agent     # the judgement calls
npm run triage:measure   # score the rules against ground truth

The ground-truth fixture

src/targets/<app>/tests/triage-fixture/ holds specs that are meant to fail, with causes known in advance. They do not run in the normal suite — the triage-fixture project exists only when TRIAGE_FIXTURE=true — so a green pipeline stays green. Each declares the category it should produce: 

annotation: [
  { type: 'practitest', description: '5904' },
  { type: 'triage-ground-truth', description: 'network-infrastructure' },
]

The expected category is an annotation rather than something the pack exports, because framework code may not import a target pack — and annotations already reach run-result.json verbatim. So a fixture added to any target is measured by the same command with no framework change.

Three outcomes, and they are not the same thing

OutcomeMeansFails the command
AgreedA rule settled it as the fixture says.no
ContradictedA rule settled it as something else. Exactly one of the two is wrong, and it is usually the rule.yes
DeclinedNo rule matched. Correct where the cause is a genuine judgement call — the model exists for those.no

A ground-truth spec that passes is reported separately: the fixture has stopped reproducing a cause it claims, so its category is unmeasured rather than agreed. A decline exits zero — a command that failed on those would train people to ignore it.

Singletons are not a rate

Before treating an intermittent failure as real, get a rate: src/support/quarantine.ts and FLAKE_MINIMUM_RUNS exist for exactly this. And ask which outcome is the honest one — an intermittent red sometimes means the passes are the defect. That is what happened to the accessibility suite.

17

Reporting and publishing

A run produces one versioned model, and everything downstream reads that rather than re-deriving it. 

npm run report:normalise   # raw results → the canonical run model
npm run report:render      # the human-readable report
npm run publish:practitest # results back against the case ids
npm run publish:jira       # back to the story
npm run notify:teams       # the card
npm run notify:email       # the digest

Reporting is best-effort by design: a failure to publish degrades to a warning plus an artifact, and never turns a green suite red. The API envelope shapes the client rather than being a detail — PractiTest takes at most 20 instances per POST and 30 calls a minute across reads, writes and attachments, so results are chunked and one token-bucket limiter is shared by the whole process.

Nothing leaves without being scrubbed

Failure messages and attachments pass through redaction before they reach a test management system. Doing Vault properly and then base64-ing an unscrubbed trace of a login flow into PractiTest would defeat the entire exercise. Attachments are failures only, size-capped before encoding, because traces are large.

An expired token is its own named condition rather than a generic request failure — otherwise a nightly run quietly stops reporting and nobody notices for a fortnight.
