How the pieces fit

One core, many applications, one path through.

Framework code never names an application; an application is a profile and a pack that the framework discovers. This page shows where that boundary sits, how a spec gets its verbs, and what actually happens between npm run onboard and a result landing back in PractiTest.

01

The boundary that everything else follows

Three regions. The arrows that do not exist are the design.

  • reads / calls
  • writes or generates
  • discovers at runtime
The consequence worth stating

Because the arrow does not exist, every capability the core offers has to be expressed as configuration a profile declares rather than a branch on a name. That is what makes the same fixtures, reporters, triage rules and publishing paths work for the sixth application as for the first.

02

How a spec gets its verbs

A spec imports one thing. Everything else is injected, and each hop has a rule that a machine checks.

FixtureGives the spec
targetThe resolved profile — base URL, capabilities, environment, roles.
runRun identity and unique-value helpers, so created records are traceable and cleanable.
secrets · secretStoreCredential lookup by reference. The value never appears in a spec.
accounts · accountSlot · roleWhich identity this worker holds, leased atomically on a pooled target.
authedPageA page already carrying the role's session.
api · apisThe primary typed client, and the other services by name. Response-schema validation is inside them, so every call is a contract check for free.
dbRead-only database access, when the capability is on.
contractsThe vendored contract document, when the target publishes one.
a11yAccessibility scanning against the declared standard. Returns findings; asserts nothing.
otp · inboxMFA codes however this target does MFA — or a refusal with a reason.
03

End to end, and what each stage leaves behind

npm run app:journey -- --target=<app> walks all six. The artifacts on the edges are what makes a skipped stage detectable.

Why the artifacts matter

Stage 2 once passed by pulling another application's story, because it took the first file on disk rather than asking this target's specs which story they cite. A stage that exists to catch “traced to nothing” must not be satisfiable by “traced to somebody else” — so each stage is checked against an artifact that names the application.

04

What happens to a failure

Group it, settle what a rule can settle, and decline the rest. Declining is a correct outcome, not a shortfall.

05

The dashboard is seven pages, not one

npm run onboard opens the wizard, but the same local server serves the operational surface beside it.

PageFor
/onboardThe wizard. Reads the running application, then writes the profile, pack, contract document and credentials.
/runsRun history, and a live view of one in progress.
/triageClusters and their verdicts, and recording what a person decided — which is what tightens a rule.
/casesCases with no spec, orphans, and what is automated.
/storiesStories and their acceptance criteria, with drafts.
/usersTest users: which accounts a profile implies, and where each credential lives.
/publishWhat is about to be pushed back, and what is unannotated.

Every page is held to four budgets measured on the rendered page rather than reviewed by eye — contrast in both themes, height, copy (34 words per explanatory block, 220 visible per page) and line length. Each budget was written after something got past a green suite.

Removing an application is a first-class operation

npm run target:remove plans before it removes, names how many files git has never seen, and does nothing until the target's own name is typed back. That is what makes it reasonable to point main at a live application: try one, drive it, and put the repository back.

06

Where a change belongs

The question to ask about any fix: which mechanism produced this artifact, and is that mechanism right?

You want to…ChangeNot
Support a new kind of applicationA capability in config/targets/types.ts and the code that reads itA branch on a target name
Fix a locator the scaffolder guessed wrongThe probe that derives it, or the templateThe generated locator
Make a failure diagnosableThe action or reporter that produces the messageThe spec that hit it
Catch a bad state earliertarget:doctor, healing, or a triage ruleA patched pack
Add coverageSpecs and the verbs they need, in the pack— this is the exception, and it is the point of a pack
Change a conventiondocs/CONVENTIONS.md, then npm run instructions:buildCLAUDE.md, AGENTS.md or the Copilot file

If the framework genuinely cannot express a fix, that is the finding: raise it as framework work and say what is missing. “It was quicker in the pack” is not a reason, and neither is “only this application has the problem” — the second one is nearly always false and is exactly how it stays hidden.
